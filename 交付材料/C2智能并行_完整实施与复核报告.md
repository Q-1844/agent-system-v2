## 1. 一句话结论

这次补完的确是以前遗漏的一层：**C2 全自动项目 Controller 与 Scene Controller 的真正依赖感知调度**。此前的 Producer 原生视频批量工具能同时提交两路 JobQueue，但 C2 Controller 仍可能一次只运行一个场景、一个镜头。这次修改了实际 Controller 循环，而不只是调大 worker 数字。

新的规则是：**Producer 决定创作上的 `allow` / `required_serial` 和每场景的并发上限，执行器把真实视频／尾帧依赖作为不可绕过的硬边，随任务完成动态调度。** 复用现成图片/视频/角色素材不意味着必须串行；只有需要另一个镜头新生成结果的镜头才等待。

## 2. 运行模式及实例

- 每个镜头的计划有 `parallel_preference`：`allow` 或 `required_serial`。Producer 可以要求特定镜头额外串行；不能通过 `allow` 消除 `inherit_previous` / `reference_previous` / `prev_tail` 的真实依赖。
- 新自动规划的每场景 `max_parallel_shots` 默认可为 2（允许降到 1）；项目级 `max_parallel_scenes` 新运行默认 2。两层是 Controller 任务调度容量，不等于绕过独立 JobQueue 的供应商并发门。
- C2 工作流的 `media_inflight` 默认是 2，JobQueue 在途视频 worker 实际数量由 env/config/已冻结的执行档位决定，Agnes RPM 与每日真实额度另外控制。**旧已冻结任务仍使用原来写入的并发档位**；不能为追求并行而改写旧请求身份。
- 影片顺序示例：A1 与 A2 是两个独立镜头；B1 需要 A1 的实际尾帧；B2 独立使用已经保存的角色 Look。A1、A2、B2 可随容量同时执行。A1 完成并生成新的可用尾帧以后，B1 可立即开始，而无需等 A2 结束或等待整个 A 场景完成。
- 如上游在本次 Run 重生视频，项目中仍保留的旧 ACCEPTED 视频**不能**让下游抢跑；必须比对当前 child 的镜头状态及其新视频版本。

## 4. 与阶段二修复的关系

修订操作**不在并行 worker 内自由写入项目**。专家可并行给出只读提案，Producer 批准后才提交修订；如果有正在提交或结算的视频任务，先保留队列意图和媒体回执并进行安全对账，再启用修订后的有效计划。

- 新增／拆分镜头后，下一次 Run 冻结新镜头顺序与新的 `prev_tail` 前驱；不会直接覆盖初始蓝图或旧 ACCEPTED 视频版本。
- 对受影响及其有因果依赖的镜头重新制作；无依赖的已接受视频可继续复用。
- job 入队时会携带来源尾帧/版本快照；JobQueue 真正提交与结果写回之前再次验证，防止排队期间素材被重新选择。
- `UNKNOWN` 视频提交及已产生供应商任务遵循原有恢复／对账逻辑，而不是为了并行盲目重发。
- 当前宽松的画质审核和此前提高的文本、图片、视频任务授权保持原样，没有趁机新增成本约束。

## 5. 发现并修复的风险点

1. 原项目与场景 Controller 存在实质串行瓶颈：扩容 JobQueue 并不足以让 C2 两路真正有任务可执行。
2. 如果仅把跨场景依赖折叠为「整个上游场景完成」，会误伤同场景里的独立镜头；现在按镜头 DAG 解锁。
3. 旧 ACCEPTED 尾帧可能提前满足一个正在重做的上游镜头依赖；现要求本次 child 的完成状态＋实际版本匹配。
4. 依赖的上游失败时，下游等待不能永远挂住；会明确阻断并由父 Run 收敛成失败/阻断状态。
5. 父 Run 在创建 child 以后、记录 `child_run_id` 以前崩溃时，恢复必须优先找回原 child，不能创建第二份。
6. 参考素材/`prev_tail` 标记在冻结后更改会改变依赖图；新 Run 额外冻结这份选择，旧 Run 继续使用旧 checkpoint 的兼容规则。
7. 独立镜头的并发状态以每镜原子更新写入，暂停/取消不会被兄弟镜头写回覆盖。

仍未由这边完成的验收：

- **真实 Agnes 长片**：不存在真实付费生成、真实限流波动、成片画面质量证明；这要通过后续真机任务验收。
- **旧已冻结 C2 任务的并发档位**：恢复遵守原始 1 路或 2 路记录，不能为了新功能强行改变历史任务；新工作流默认 2 路。
- **单进程全仓混跑**：旧 FullProject Autopilot 测试与其他测试混在一个 pytest 进程时曾有顺序相关停滞，因此对主要测试目录和这组旧测试分别执行。分组完整覆盖不等于混在一个进程也已排除该历史问题。
- **跨场景继承的规划入口**：默认 Scene Planner 仍保持「每个场景第一镜独立」的旧创作约束；执行层能正确处理已经明确写入计划的跨场景尾帧依赖，但此次不改变这一条故事规划规则。
