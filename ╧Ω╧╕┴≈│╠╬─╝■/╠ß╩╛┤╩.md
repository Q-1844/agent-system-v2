==================================================
一、本阶段最重要的边界
===========

AI-4B 不再新增新的 AI Specialist。

它不是 Agent 决策层。

它是：

**确定性执行引擎。**

职责：

```text
approved Production Plan
        ↓
Scene Autopilot Run
        ↓
按依赖执行每个 Shot
        ↓
自动生成提示词
        ↓
自动生成 / 选择首帧
        ↓
按计划生成尾帧
        ↓
自动生成视频
        ↓
自动设为本 Run 的最终视频
        ↓
实际视频末帧
        ↓
下一个 Shot
        ↓
Scene completed
```

不要让 Executor 自己重新判断：

* 是否应该新增 Shot
* opening_source
* link_mode
* 是否需要尾帧
* 是否应该改变故事
* 是否应该改变角色

这些已经由：

AI Director + Production Planner

完成。

Executor 只执行 approved plan。

==================================================
二、第一版调度策略：严格逐 Shot 串行
=====================

虽然 Agnes Probe 已证明视频 outstanding 并发可用，本阶段仍然采用：

```text
Shot 1 完整结束
↓
Shot 2
↓
Shot 3
↓
...
```

不要跨 Shot 并发执行：

* first frame
* last frame
* video

不要实现 outstanding video submitter。

不要同时跑两个 independent Shot。

原因：

第一版先验证：

* continuity
* checkpoint
* recovery
* 自动候选
* 无人值守

真正稳定。

但是内部实现不能把架构写死成：

```python
for shot in scene.shots:
    await execute_everything(shot)
```

应该写成一个简单 dependency scheduler。

第一版 scheduler 的策略只是：

> 从所有 dependency 已满足的 Shot 中，按 Scene 顺序只选择第一个执行。

例如：

```python
def next_ready_shot(run, project):
    ready = []

    for state in run.shots:
        if state.status in TERMINAL:
            continue

        plan = run.plan_for(state.shot_id)

        if dependencies_satisfied(run, project, plan):
            ready.append(state)

    if not ready:
        return None

    return min(ready, key=lambda s: s.index)
```

以后改成多路并发时：

只需要改变 ready Shot 的放行数量。

不要重写整个 Executor。

==================================================
三、增加正式的 SceneAutopilotRun
=========================

Production Plan 是：

“准备怎么做”。

Autopilot Run 是：

“这一次实际做到了哪里、生成了什么”。

两者必须分开。

建议：

```python
class SceneAutopilotRun(BaseModel):
    run_id: str
    project_name: str
    scene_id: str

    plan_id: str
    plan_snapshot: dict

    # 每次新 Run 都不同
    run_seed: int

    status: str

    respect_locked: bool = True

    pause_requested: bool = False
    cancel_requested: bool = False

    current_shot_id: str | None = None
    current_stage: str | None = None

    shots: list[ShotExecutionState]

    error: str | None = None

    created_at: float
    updated_at: float
```

Run status 第一版建议：

```text
pending
running
pausing
paused
blocked
failed
completed
cancelled
```

`blocked` 用于：

* Production Plan / Shot 结构在运行过程中被外部修改
* dependency 已无法满足

不要把这些情况误报成 Agnes generation failed。

==================================================
四、ShotExecutionState
====================

每一个 Shot 都必须有本 Run 自己的 checkpoint。

不要只看：

```text
shot.first_frame.ready
shot.video.ready
```

因为它们可能属于以前的手工生成或以前的 Run。

建议类似：

```python
class ShotExecutionState(BaseModel):
    shot_id: str
    index: int

    status: str
    stage: str

    active_job_id: str | None = None
    active_stage_key: str | None = None

    first_prompt: str | None = None
    first_batch_id: str | None = None
    selected_first_candidate_id: str | None = None

    last_prompt: str | None = None
    last_batch_id: str | None = None
    selected_last_candidate_id: str | None = None

    video_prompt: str | None = None
    video_version_id: str | None = None

    source_video_version_id: str | None = None

    attempts: dict[str, int] = {}
    warnings: list[str] = []

    error: str | None = None
```

Shot status 可以：

```text
pending
waiting_dependency
running
skipped_locked
failed
completed
```

stage 建议：

```text
activate_plan

first_prompt
first_frame

last_prompt
last_frame

video_prompt
video

video_end

done
```

不需要生成的阶段记：

```text
skipped
```

而不是假装 done。

==================================================
五、新 Run 和 Resume 必须完全区分
=======================

这是本阶段最重要的不变量之一。

---

## A. 新 Run

用户点击：

```text
开始自动制作
```

创建新的 run_id。

新 Run 必须生成新的：

* prompt
* first-frame batch（计划需要时）
* last-frame batch（计划需要时）
* video version

即使 Shot 已经存在：

```text
首帧批次 1
尾帧批次 1
视频 v1
```

新 Run 仍然产生：

```text
首帧批次 2
尾帧批次 2
视频 v2
```

不得因为：

```text
shot.first_frame.ready == True
```

就跳过。

---

## B. Resume

如果同一个 run_id：

```text
c01 completed
c02 completed
c03 failed at video
```

用户点击：

```text
继续执行
```

必须：

```text
从 c03 的 video checkpoint 继续
```

不得重新：

* c01
* c02
* c03 first frame
* c03 last frame

因此：

**是否跳过阶段由 Run checkpoint 决定。**

不是由 Shot 当前 ready 状态决定。

==================================================
六、Run seed
==========

AI-4A Production Plan 已有 plan.run_seed。

但是不要让所有基于同一 Plan 的新 Autopilot Run 都直接使用同一个 seed。

否则：

Run #1
Run #2
Run #3

可能一直自动选择相同 candidate index。

每个 SceneAutopilotRun 必须拥有自己的稳定：

```text
run_seed
```

推荐根据：

```text
plan.run_seed + run_id
```

确定性派生，例如：

```python
def derive_execution_seed(plan_seed: int, run_id: str) -> int:
    raw = f"{plan_seed}:{run_id}".encode("utf-8")
    digest = hashlib.sha256(raw).digest()
    return int.from_bytes(digest[:4], "big") & 0x7fffffff
```

这样：

* 一个 Run 内重启后 seed 不变
* 不同 Run 得到不同选择
* 不依赖 Python hash()
* 可复现

Run 文件保存最终 run_seed。

==================================================
七、Plan Snapshot 必须被冻结
=====================

Run 创建时：

不要让 Executor 后续一直读：

```text
production_plans.json
```

作为执行依据。

要将 approved plan 完整 snapshot 到 Run。

例如：

```text
plan_snapshot
```

原因：

用户可能在 Run 执行期间重新打开 Production Planner。

运行中的 Run 应继续执行：

> 它开始时确认的那个 Plan。

新 Plan 只影响下一次 Run。

==================================================
八、开始 Run 前的 preflight
=====================

POST start 时必须：

1. load Project
2. 找 Scene
3. 找 approved Production Plan
4. 确认 plan 不 stale
5. Shot structure 与 plan snapshot 一致
6. Scene 至少有 1 个 Shot
7. 没有同 Scene 的 active Run
8. 检查 locked Shot
9. 创建 run file
10. 启动后台 Executor

不要创建 Run 后才发现：

```text
Production Plan stale
```

## locked Shot

第一版建议支持：

```text
respect_locked = true
```

默认开启。

开始确认 UI 提供：

```text
☑ 保留已锁定镜头
```

如果 locked Shot 已经存在：

```text

```

则：

```text

```



不要等 Run 跑到中间才发现。

如果 locked Shot 连最终视频都没有：

第一版建议同样阻止 start，而不是产生“完成但缺镜头”的 Run。

十、dependency 判断
===============

使用 Production Plan 中：

```text
requires_previous_video_end
source_shot_id
```

但 runtime 仍要验证真实项目状态。

例如：

```python
def dependency_ready(project, planned):
    if not planned.requires_previous_video_end:
        return True

    source = project.get_shot(planned.source_shot_id)

    if not source:
        return False

    if not source.final_video_ready:
        return False

    if not source.video_end_frame.url_ready:
        return False

    return True
```

字段名称根据当前真实 models 调整。

如果 source Shot 是本 Run 生成：

必须使用本 Run 刚刚自动设为 final 的视频版本。

如果 source Shot 是 skipped_locked：

使用当前已有 final video。

==================================================
十四、first frame
==============

如果：

```text
planned.generate_first_frame == True
```

调用现有首帧 JobQueue 逻辑。

不要重写 Agnes Image 调用。

新 Run 必须创建：

**新的 first-frame batch。**

即使 Shot 已经存在旧批次。

Autopilot 不等待用户选择。

Job 完成后：

1. reload Shot
2. 找到本 Run 创建的 batch
3. 获取成功 candidates
4. 调用 seeded auto selection
5. 使用当前 choose-first 业务逻辑正式选择
6. 保存 selected candidate id 到 Run

==================================================
十五、不要用“最新数组最后一项”猜本 Run 输出
=========================

这一点非常重要。

不要：

```python
batch = shot.first_frame_batches[-1]
```

并假定一定属于 Autopilot。

用户、旧任务或恢复过程都可能造成混淆。

优先使用当前生成 service / Job result 已有稳定：

```text
batch_id
version_id
```

如果当前 JobQueue handler 完成后无法把 stable output id 返回给 Executor，请做最小改造。

优先级：

### 优先方案

Job terminal result 能提供：

```text
batch_id
video_version_id
```

Executor 直接记录。

### 如果当前 JobQueue 不保存 handler result

允许增加最小、向后兼容的 job metadata：

```text
origin = "scene_autopilot"
origin_run_id
origin_stage_key
```

生成 batch / video version 时同步记录：

```text
origin_run_id
```

然后 Executor 精确找到本 Run 输出。

如果当前 batch / version 数据模型没有任何 metadata 槽位，可以增加一个：

```python
origin_run_id: Optional[str] = None
```

默认 None。

旧项目自动兼容。

不要为了这个能力大规模重构所有 Asset。

核心要求只有：

> Run 必须准确知道“哪个批次 / 哪个视频版本是我生成的”。

==================================================
十六、Job idempotency / 防重复提交
==========================

Backend crash 最危险的窗口：

```text
Executor enqueue video job
↓
JobQueue 已持久化
↓
Executor 还没来得及保存 active_job_id
↓
进程崩溃
```

恢复后如果直接重新 enqueue：

可能重复提交视频。

所以 Autopilot 调 JobQueue 时必须使用稳定 stage key。

例如：

```text
autopilot:{run_id}:{shot_id}:{stage}:{attempt}
```

如果现有 Job model 已支持 metadata / payload：

加入：

```text
origin_run_id
autopilot_stage_key
```

恢复 / enqueue 前：

先查当前 JobQueue：

```text
是否已经存在相同 stage key 的 queued/running/done job
```

存在：

复用 job_id。

不存在：

才创建。

不要大规模重写 JobQueue。

只增加完成 Autopilot crash safety 所需要的最小 optional metadata / lookup helper。

尤其 video stage 必须做到：

**同一个 Run stage 不会因为进程重启重复 POST /v1/videos。**

==================================================
十七、等待 JobQueue
==============

Executor 不直接 poll Agnes。

视频仍由当前 video handler / JobQueue：

```text
create_video
→ video_id 落库
→ poll
→ download
→ video_end extraction
```

负责。

Executor 只等待 JobQueue job terminal。

可以增加内部 helper：

```python
async def wait_for_job(job_queue, job_id):
    while True:
        job = job_queue.get(job_id)

        if job.state in {"done", "failed", "cancelled"}:
            return job

        await asyncio.sleep(0.5 or 1.0)
```

根据当前 JobQueue API 调整。

不要通过 HTTP：

```text
GET /jobs
```

轮询自己。

```text
video_prompt
```

继续使用当前实际：

```text
Shot.target_duration_s
```

和 `_collect_prompt_context`。

Autopilot 新 Run：

必须重新生成。

Resume 本 Run：

已有 video_prompt checkpoint 时复用。

==================================================
二十三、video generation
====================

继续复用当前：

```text
video JobQueue handler
```

不要写第二套 Agnes Video 逻辑。

第一版：

**一次只运行当前 Shot 的一个 video job。**

即使 Probe 已证明 Agnes 可 outstanding。

本阶段禁止：

```text
submit next video while current video running
```

以后性能优化只修改 scheduler。

==================================================
二十四、视频失败的 retry 特别注意 video_id
=============================

视频 job failed 后允许：

```text
1 次 Executor-level retry
```

但是不要简单“重新 POST 一个新视频”。

必须先利用当前已有的：

* video_id 持久化
* recover_pending_videos
* JobQueue retry semantics

判断：

如果失败只是：

```text
本地轮询 / 网络 / 进程问题
```

且已经存在可恢复：

```text
video_id
```

优先继续 poll 原 Agnes task。

只有当前正式 video handler 判定：

原任务已经不可恢复 / terminal failed

才按照当前视频版本机制产生下一次 retry。

不要破坏当前已经验证过的“有 video_id 不盲目重提交”原则。

==================================================
二十五、Autopilot 生成的视频必须自动成为 final
===============================

视频成功后：

Run 必须知道本次：

```text
video_version_id
```

然后通过当前现有：

```text
set-final
```

业务逻辑，将本 Run 新视频版本设为当前最终视频。

不要重新实现 final selection。

必须复用现有：

```text
video/set-final
```

背后的 service/helper。

不要通过 HTTP 调 localhost。

如果 set-final 当前逻辑仍在 Router，做最小提取。

原因：

下一 Shot 的：

```text
source_version
video_end_frame
continuity
```

必须绑定到本 Run 刚刚生成的视频。

==================================================
二十六、视频实际末帧
==========

set-final / video handler 完成以后检查：

```text
video_end_frame
video_end_source_version
```

是否对应：

**当前 Run 刚刚设为 final 的 video version。**

如果：

```text
video_end_frame.url ready
```

记录 video_end stage done。

---

## 如果 extraction / host 失败

如果下一 PlannedShot：

```text
requires_previous_video_end == True
```

那么：

1. 自动调用现有 video-end refresh helper 一次
2. 再检查
3. 仍失败：

```text
Run failed
```

原因：

下一镜硬依赖它。

如果下一镜：

```text
independent
```

那么当前末帧失败不一定需要让整 Scene failed。

可以：

```text
Shot completed_with_warning
```

Run warning：

```text
视频已完成，但实际末帧提取失败。
后续镜头不依赖它，因此继续制作。
```

不要因此删除成功的视频。

==================================================
二十七、dependency source 必须来自本 Run 的结果
===================================

假设：

```text
c01 原来已有视频 v1
```

本 Run 新生成：

```text
c01 v2
```

然后：

```text
c02 inherit_previous
```

必须使用：

```text
c01 v2 的 video_end_frame
```

不能误用旧的 v1。

因此：

* video_version_id 记录进 c01 Run state
* c01 v2 自动 set final
* video_end_source_version 必须 == v2 version id
* c02 activate 时 source_version 绑定 v2

如果版本不一致：

不要继续。

这属于 Run consistency failure。

==================================================
二十八、respect_locked
==================

如果：

```text
respect_locked = True
```

locked Shot：

不生成新 prompt / image / video。

标记：

```text
skipped_locked
```

并记录：

```text
当前 final video version
```

如果后续依赖它：

要求当前：

```text
final video ready
video_end_frame.url ready
```

前置 preflight 已尽量检查。

如果运行期间状态变化导致不可用：

Run blocked / failed，给明确错误。

==================================================
二十九、暂停
======

提供：

```text
暂停
```

但不要强制杀死当前 Agnes job。

行为：

```text
pause_requested = True
status = pausing
```

如果当前：

* Agnes text request
* image job
* video job

正在执行：

允许它正常完成并保存结果。

到下一个 stage checkpoint 时：

```text
status = paused
```

不再提交新工作。

这样：

* 不浪费已提交任务
* 不制造半资产
* 恢复简单

==================================================
三十、Resume
=========

paused / failed Run：

提供：

```text
继续执行
```

Resume：

* 使用同 run_id
* 使用同 run_seed
* 使用同 plan_snapshot
* 已完成 stage 不重新跑
* 已生成 batch / version 不重新建
* 从第一个未完成 checkpoint 继续

如果 Run failed 在：

```text
video
```

且用户点击继续：

遵守 video retry / recovery 规则。

如果失败已经达到 max attempts：

可以要求：

```text
重新尝试当前阶段
```

增加 attempt。

不要自动创建新 Run。

==================================================
三十一、停止自动制作
==========

提供：

```text
停止自动制作
```

行为：

```text
cancel_requested = True
```

当前 active job 与暂停一致：

允许当前已经提交的任务完成并保存。

checkpoint 后：

```text
status = cancelled
```

不要：

* 删除刚生成图片
* 删除视频
* 恢复旧 final
* 回滚 prompt

已经成功产生的东西全部保留。

==================================================
三十二、后台重启恢复
==========

这是本阶段硬要求。

Run 持久化建议：

```text
projects/{project}/output/ai/autopilot_runs/{run_id}.json
```

每个 Run 一个文件。

这样以后 ProductionRun 可以直接引用这些 Run。

不要只保存：

```text
latest_autopilot.json
```

历史 Run 不能覆盖。

## startup

在现有 app / JobQueue startup recovery 后：

扫描所有项目：

```text
output/ai/autopilot_runs/*.json
```

查找：

```text
running
pausing
```

Run。

对每个 Run：

重新调度 Executor recovery。

## 恢复 active job

如果 Run 有：

```text
active_job_id
```

先查询 JobQueue。

如果：

queued / running：

不要重新 enqueue。

继续等待。

如果：

done：

reconcile Shot / batch / video output
→ 标 stage done
→ 继续。

如果：

failed：

进入 retry policy。

如果 Job 已不存在：

先通过：

```text
autopilot_stage_key
origin_run_id
```

查询 persisted JobQueue / output。

找得到：

复用。

确定找不到且没有本 Run output：

才允许重新执行。

视频 stage 尤其禁止盲目 resubmit。

start 时必须确保 Plan：

```text

not stale
```

```text

```

不要自动 replan。

```text

```

避免 Resume 后无法解释外部修改。
