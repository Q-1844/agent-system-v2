## 为什么上次修复后仍会停

D仓 [42288322191](https://github.com/Q-1844/agnes-frame-host/actions/runs/42288322191) 构建成功，但deploy再次在600000ms超时，最后状态errored。`objects/6c9d6e557631dd22.jpg` 已存入仓库但未发布。

PR #51纠正了「Contents命中便宣称Pages可用」的误判，保住了视频输入的真实性，但只把假成功改成真实等待。失败的部署并不会因重复GET、三次重试或20分钟等待而自行重建。等待耗尽后，driver又将视频后处理的基础设施异常记成普通FAILED，巡检按设计不再接棒。这是上轮修复遗漏的完整生命周期。

此前多日故障也并非只有配额逻辑：状态白名单、三级暂停标志、提交收据、定时唤醒、供应商瞬态和图床部署属于不同边界。短mock及源码结构断言未贯穿「真实失败 → 保存 → 自动恢复 → 最终合成归档」全链。RESTORED或新增回执只能证明局部接续，不能替代成片验收。

## 本轮实现

- 图床遇到持续未发布时查询Pages构建状态。仅对确认errored的legacy部署、且其发布分支与本图床配置一致时请求重新构建；不重启building/queued或无关分支，不再PUT同一图片，不重拍视频。
- 同一图床实例共享锁、查询冷却和失败部署身份。并发waiter对同一次失败只请求一次重建，POST响应丢失也不盲目重复。控制API权限/网络异常不被当作发布成功；公网200仍是必要条件，公网请求不携带凭据。
- 独立的`output/infrastructure_waits/`账本以`MEDIA_PUBLICATION_PENDING`保存明确的Pages超时原因及镜头/视频版本/本地帧SHA256。driver只检查当前FullRun→ProjectRun→SceneRun中失败镜头的当前完成视频，验证版本、本地视频和末帧存在，避免把历史错误或内容问题误分为基础设施等待。
- 保留三次末帧重试、120s退避、1200s终试等待及其结构测试；耗尽后先排水，再保存`INTERRUPTED / technical_wait / asset_publication`并走原nonce的自动续跳。完成事件唤醒和巡检也能接棒，不新增状态白名单。
- 诊断不扩展冻结的Asset结构、不改project.json或视频输入签名，保持旧检查点兼容；恢复不改创作计划、已付费任务身份或选版。
