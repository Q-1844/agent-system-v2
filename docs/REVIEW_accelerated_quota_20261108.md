# 可重复的压缩额度接续测试

## 原始事故和修复范围

GLM在`film3m-42394136215`发现215跳空转，已补齐paused分支对Job额度闸门的识别。本轮继续核对：仅修改B1的`quota_resume_after`不会改变artifact里Job的旧闸门；仅改`DAILY_VIDEO_SECONDS`也不会在同一天刷新其用量。两者都不足以反复模拟跨日。

新增显式、按nonce冻结的`quota_test_policy`。新任务派发时设置`daily_video_seconds=60`及`quota_test_wait_minutes=2`，即可执行“小额度耗尽→原生额度暂停→排水→workflow_run唤醒→恢复快照→继续下一镜”的真实链路。默认等待参数为0，关闭此功能。策略由检查点继承，自动续跳不依赖重复传入测试参数。

## 账本和恢复纪律

- 测试窗口和真实日账本独立。窗口刷新只清零窗口用量；真实视频日用量继续累计，真实500秒硬墙优先。
- 窗口在首次拒收时确定刷新时间，重复检查不延后。策略及窗口状态随原artifact恢复。默认生产进程不会仅凭缓存中的测试元数据激活模拟。
- 原生视频预检和HTTP客户端使用同一结构化额度事实，不靠错误文案猜测短闸门。在取得限流槽后再次检查本地额度，避免排队请求使用旧余额。
- 只有有效测试策略、`WAITING_QUOTA/quota_exhausted`和`quota_wait_source=test_window`共同成立时，唤醒使用现有一分钟environment timer；每次仍检查完整日期闸门。真实供应商拒收继续使用正常跨日闸门及20分钟timer。
- 保留GLM的`b1-test-ops`，增加CAS留存的原/新闸门、nonce及源owner证明。恢复时仅同步本项目、daily_quota、not_sent、无任务号、精确匹配旧闸门的Job。已受理、UNKNOWN及其他项目不可放行。原闸门保留在Job历史中，记录随源恢复链保留，覆盖runner再次死亡的窗口。
- 连续三次无新增受理或完成进展的恢复触发20分钟技术退避，使用独立`resume_not_before`，避免高生命周期跳数上限再次变成快速空转。正常额度等待不消耗此计数。

未修改Asset结构、创作输入签名、文本输出上限、原视频版本或末帧三次重试加20分钟终试政策。

## 真实验证

最终全量与GitHub实测结果另记C仓交接。检查点必须显示多次WAITING_QUOTA→新owner RESTORED/RUNNING，且新增有效视频、既有回执及文件SHA一致，才能算穿越窗口。派发204、RESTORED或受理本身均不代表成片完成。
