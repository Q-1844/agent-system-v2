# 服务端反馈接入 Producer 自主修复（2026-11-17）

## 结论与缺口

用户要求：自有审核打回与供应商内容驳回都应上报 Producer，由 Producer 自行或组织
相关 agent 修改提示词、镜头或局部剧情；再次被拒就继续修订。不同平台限制不同，
不能写固定的提示词禁词表。

审查基线 `7fa237c` 存在两处明确缺口：

1. CP-3 的第三批改写失败后仍回到 FullProject FAILED，缺少到既有修复链的入口。
2. 驱动只在 `c2_source_project` 下调用既有 Producer 修复桥，新建影片被排除。

此前关于“三批失败后停机报警即可”的判断不完整。本次沿用现有协作决策、R3/R4
修订日志、CAS、原生 FullProject/Scene/JobQueue 执行器，补齐反馈入口和恢复闭环。

## 最终行为

1. 从当前 FullRun → ProjectRun → SceneRun → 实际失败 Job 核对来源。只接受匹配的
   首帧、尾帧或视频内容驳回，保留供应商错误原文、实际送出的提示词、平台/模型与回执。
2. 低层批次仍不能解决时，将其作为真实审核 finding 交给 Producer。Producer 按冻结的
   协作模式自行修订或选择导演/编剧等角色；专家提出局部方案，由 Producer 选择批准。
3. 获批后先 CAS 追加修订，再应用到同一项目，启动后续原生 FullRun。未受影响的完成
   素材继续锁定复用，原视频版本和供应商回执保留，Stage0 身份不重写。
4. 后续请求仍被拒时生成新的 finding，再次进入 Producer 修订；上下文携带以前的修订
   和决策结果。没有“两次修订后永久停止”的创作上限，也不允许换个 Job ID 重发原文
   冒充修复。仅改时长而不改被拒内容的方案不会获准提交。
5. 方案无效、Producer 尚未批准或文本模型暂不可用时，保存 `repair_pending_finding`、
   决策历史与排水结果，进入带冷却的 `INTERRUPTED/technical_wait`。沿用原巡检和唤醒
   链自动接棒；恢复先继续修订决策，不先重启旧生成请求。
6. 保留所有权、CAS、取消语义和对账保护。UNKNOWN/在途视频不能当作已拒收；已受理
   视频必须有确定的供应商失败事实，才可进入此创作修复流程。额度、网络、图床等仍
   使用既有基础设施恢复路径。

## 关联修补

- 普通 create 模式也会回放同一份修订账本和有效计划，支持“CAS 已提交、项目尚未写入”
  的崩溃恢复，保持原蓝图与最终时长验收门槛。
- 方案支持按阶段明确修改/清除 `prompt_overrides`，避免叙事已改、旧 override 仍覆盖
  实际请求。此选择来自获批方案，不是机械删改提示词。
- 原生 first-prompt 阶段会生成新的英文文本。现在先记录绑定到修订及语义来源的文本
  哈希，再写入生成结果，恢复时识别正常派生文本；未记录的文本改动仍被拒绝。
- 队列保留异常 body，避免短错误文本截断审核代码；重试/重新执行时清除旧错误回执。
