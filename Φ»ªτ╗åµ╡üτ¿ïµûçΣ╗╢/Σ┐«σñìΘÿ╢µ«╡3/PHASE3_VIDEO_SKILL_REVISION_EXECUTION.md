# 第三阶段：视频连续生产 Skill 修订与验收

日期：2026-09-27。将“可直接发送的提示词”单独交给能读取真实仓库的 Zcode。本文件是执行文档；本轮没有修改项目中的 Skill。

## 输入结论与一个新的风险

- 第一阶段审计：Crane_Lake_P40A 的实际生产模型为 agnes-video-v2.0；multi 仅能消费一张视频语义参考，i2v 的单张首帧是另一种输入。该仓库的 2.5 reference 多图通路尚未实现、未做视觉验证。
- 第二阶段实验：只在 Crane_Lake_P40A_expB 克隆内，用已批准场景图、Look、s02_c01 真实末帧合成 s02_c02 的新首帧，再制成视频 vv_6e26ffbc。身份、体态、景别、动作明显优于裸尾帧接力；但结尾已触水站立，原 expected_tail 是空中减速，颈前羽色略偏粉。原项目 canonical 没改，s03_c01 没重做。用户认为效果非常不错，是积极的视觉反馈，不等于正式选片或允许改写剧情尾态。
- 外部核查：Agnes [2.5 官方文档](https://wiki.agnes-ai.com/en/docs/agnes-video-25)与[Flash 文档](https://wiki.agnes-ai.com/en/docs/agnes-video-25-flash)允许 reference 模式接收多张参考图，但 keyframe 的 first_frame/last_frame 与 reference 的 images 互斥；参考不锁首帧。这是官方能力，不是本仓库可执行能力。
- 特别注意：[v2.0 官方公告](https://wiki.agnes-ai.com/zh-Hans/docs/agnes-video-v20)称该模型于 2026-09-25 23:59:59（UTC+8）下线。它与第二阶段当日实验成功的记录并存，服务侧的实际适用范围未核实。下一次真实生成前须核查账户、入口、实际模型与编译请求。本阶段不发付费请求。

设计目标：在现有连续生产 Skill 建立唯一的起步/再锚定决策入口，在桥接 Skill 保留有效端点后的接缝修复职责。将模型字段和能力状态放可更新的事实表；Skill 主体只保留可复用的判断。此结构符合 [Agent Skills 规范](https://agentskills.io/specification)及 [OpenAI 对 Skills 工作流的说明](https://developers.openai.com/plugins/concepts/skills)。

## 可直接发送给 Zcode 的第三阶段提示词

~~~text
你是本项目的视频生产 Skill 维护者。只执行第三阶段：依据两份报告修订正式 Skill、必要的最小防错代码，并做无生成费用的行为验收。在真实仓库内完成修改，提交可审查的 diff 与测试结果，不进入第四阶段。

输入：
1. VIDEO_RELAY_CAPABILITY_AUDIT_P40A.md（第一阶段能力审计）
2. EXPB_FUSED_FIRST_FRAME_S02C02_REPORT.md（第二阶段克隆实验）
若仓库里没有报告，以我随提示词提供的全文为输入，不凭文件名猜内容。先用代码、配置、receipts 和项目实际资产复核报告结论。

边界：
- 不调用任何付费图片或视频生成；不续做旧桥接，不重做 s03_c01，不把 expB 候选自动提升到 Crane_Lake_P40A 的 canonical。
- 可修改正式 Skill、紧密相关的能力映射/编译校验和无费用测试。若规则与代码冲突且最小改动可测试，修代码；若范围较大，列为下一阶段的阻断项，不用文案假装修好。不要顺手迁移默认模型。
- 遵守现有 Producer/Director/Scene Agent ownership、canonical revision/OCC、resource locks、receipts、truth gates 和人工选片流程；Agent 的“已完成”不是证据。
- 先核查 full-story-relay-calibration、keyframes-bridge-repair 的真实文件、触发条件和上级规则。保留一个连续生产决策入口；桥接 Skill 用交叉引用，不复制一套竞争规则。

一、先做冲突盘点和实时能力核验

逐条对照报告与仓库，标“已证实 / 已变化 / 未确认”，至少包括：
A. multi+prev_tail 是按全片顺序还是按组寻找上一镜；组首会不会误接上一组尾帧。
B. multi 的语义参考同步到 first_frame 并 mark_done 后，改成 i2v 时会不会误消费；同路径视频末帧重提取会不会覆盖旧 local 字节。
C. reference_previous 的同场景门槛与 multi 的跨组/跨场景行为是否矛盾。
D. s03_c01 曾有合格静帧，但 multi 实际未消费该静帧；不可把“已生成首帧”当作“已输入视频”。
E. 第二阶段合成图的真实图片请求是否包含批准 Look、场景 SIV 和指定 s02_c01 video_version 的末帧；检查发送顺序、预算裁剪、临时 provenance、持久 receipt。单看 used_reference_ids 可能漏掉临时尾帧；单看 prompt 也不能证明图片进了请求。
F. vv_6e26ffbc 是否仍只在 expB；原项目 s02_c02 与 s03_c01 的已选版本、来源末帧和过期依赖。把用户“效果非常不错”记为反馈，不伪造原项目选片或剧情批准。
G. 官方 v2.0 下线公告与近期成功调用并存，记录日期与服务端事实，不推断以后持续可用；2.5 多图仍须本地编译、实际请求、视觉验收。

能力表按路径分别记录：设计可选、官方支持、本地编译可用、最近服务端成功、视觉已验证、当前项目资产已批准；每项附来源及日期。任何空白写“未确认”。

二、修订连续生产 Skill 的决策链

1. Group 是相对完整的故事段/动作过程，镜头数随剧情决定。每镜都读批准 Look、场景和 Shot 意图、上游真正已选视频版本、真实尾帧、当前画面/动作状态和依赖版本；不是只有组首做身份检查。
2. 按“叙事关系 → 上游端点质量 → 当前可用槽位”的次序决策。叙事关系区分同一动作继续、保留语境但换景别、正常切镜、新场景；端点区分身份与动作可读且正确、身份不可读但环境/动作有用、已画错、版本过期。不能用接了几镜、组号或参考数组位置替代判断。
3. 清楚定义路径：
   a. 真实尾帧作下一视频首帧边界：只在画面合格且动作确实需继承、模型/编译器支持时选；这是起点约束，仍须检查实际输出第 0 帧及中段。
   b. 裸尾帧作为单图语义参考（v2.0 multi）：不锁首帧，没有独立 Look，身份风险高时避免；不得称作硬接。
   c. Look＋指定真实尾帧（必要时加批准场景图）先经图片模型合成新首帧，再用受支持的首帧模式制视频：适用于远景身份信息不足、下一镜转中近景而上镜环境/动作仍有用。生成前检查必要参考均实际发送；审合成图的身份、空间、动作起点；保证视频真的消费选中首帧。这是保留语境的重新构图/正常切镜，不是逐像素尾帧接续。s02_c02 的实验为正例，不升级成所有镜头的默认值。
   d. Look 主导的独立首帧/新镜头：适用于新故事段、正常切镜、换场景、上镜端点错误；组内在必要时也能重建，须写清剧情代价。
   e. 原生首帧边界＋独立 Look、Look＋尾帧直接多图视频 reference：保留为未来路径，当前未接通/未验证。禁止给 v2.0 单参考槽塞两张图；2.5 reference 允许重新构图但不锁首帧，keyframe 不能混用 images。未来完成字段、编译、实际调用和视觉验收后才启用。
   f. 桥接修复仅在成片接缝审查后考虑，需两个端点自身合格且值得保留，并且确有叙事/视觉断裂；普通电影切镜不插桥，错误端点先修。
4. 在远景转中近景、实际请求已丢 Look、数镜接力后身份漂移时触发组内再锚定评估。优先让批准身份依据真正进入图片或视频请求，而非机械占据“第一张参考图”。
5. 新组首镜显式决定是否跨组延续。若 prev_tail 残留会绕过决策，先清理/显式配置并 dry-run 检查，必要时加最小 guard。跨场景使用 reference_previous 若被现有 continuity_status 拒绝，选择合法替代路径或报能力缺口，不绕过 truth gate。
6. 为 first_frame 槽区分硬边界与仅供 multi 的语义参考，记录精确来源 video_version 与不可变 URL/hash。multi 改 i2v 前重新确认该镜应消费的首帧。上游重选后把旧版本下游标成待复核：比较真实输入与新上游状态，可保留合格镜，不机械全重做，也不能沿用过期引用。
7. 生成后的视觉门槛包括身份（黑颈、红冠、黑次级飞羽及腿等该角色批准特征）、身体、场景、动作和实际尾态，以及与前镜剪辑。先查真实编译请求、sent/used/dropped refs、input_visuals、model/mode、来源版本，再看首/中/尾帧。工具成功不等于视觉合格。若身份已合格却提前触水，记为“视觉合格、剧情尾态偏离”，让负责剧情/镜头的 owner 评估重试收束或接受新尾态；只有接受后才循 canonical 流程更新预期和下游起点，不能悄悄把 expected_tail 改成已发生的动作。
8. 状态不得混淆：实验候选、用户积极反馈、正式版本选定、故事事实调整、下游批准是不同事件。

三、Skill 位置与最小代码守卫

先做最小 diff，删除或改写冲突原句。不要把实验日志和长模型参数堆进 SKILL.md；若仓库允许 references/，详细能力表在那里按模型和日期维护，主体写何时读取它。Skill 要能被“组内身份漂移”“新组首镜”“尾帧接续”这些真实任务正确触发，不要过宽触发纯桥接修复。

对以下现存风险逐个提供实际 diff 或清楚的阻断项：
- 组首 prev_tail 跨组误继承；
- multi 的 reference_only 被当成 i2v 的 hard_start_boundary；
- 尾帧同路径覆盖与旧来源版本混淆。
防错应尽量在编译或 truth gate 失败，而不是只在说明文里警告。维持兼容已有数据的最小变更，并补能证明守卫有效的无费用测试。2.5 迁移另列任务，当前阶段不暗中切换生产模型。

四、无费用的 Skill 行为验收

保留旧规则作基线；用相同中性任务描述、只读 fixture，在旧版与新版或无新规则环境分别跑决策模拟。新对话/干净上下文，让执行 Agent 自行读取 Skill，不在题干指定答案或暗示融合方法。逐例记录实际读取的 Skill、建议路径、依据、拟消费的 asset_id/video_version、槽位语义、能力校验、应由谁审批。可编译路径加编译器 dry-run 断言，不发生成任务。

至少九例：
A 组内清晰合格尾帧，同一动作继续；
B 组内远景身份不可读，下一镜中景，但场景动作有用；
C 组内上镜尾帧已画错，下一镜要求第 0 帧正确；
D 新组首镜是正常切镜，不需跨组接续；
E 新组首镜确需接续，但 prev_tail 残留且编译器按全片上一镜取源；
F multi 把上一镜尾帧同步到 first_frame，后续改 i2v；
G 上游改选新视频，下游还指向旧末帧；
H 两端合格且值得保留，组间有真实断裂；另对照一处可接受的普通切镜；
I 融合视频身份合格但尾态提前落地，尚无正式选片。

行为断言：不得调用未实现的多图视频、不得把参考图当实际第 0 帧、不得接错误/过期端点、不得自动晋升 expB 候选、不得桥接普通切镜；B 必须识别组内再锚定可能，D 允许独立起步，I 保留尾态冲突。允许几种合理路径并列，但须说明能力和叙事条件。失败则修规则/最小守卫后复测同一 fixture。比较旧版、新版的错误数、漏触发/误触发、文本成本；客观断言结合人工检查实际解释，而非只打总分。

五、交付并停止

1. 权威文件、修改前后关键 diff（原句→新句→原因）及必要的代码守卫/测试。
2. 路径能力表五种状态和证据日期；明确 v2.0 下线风险、2.5 多图尚未在本地可用。
3. 九例以上的旧/新行为对照、编译 dry-run 结果、失败/修正及 Skill 触发情况。
4. expB 与原项目的版本状态、s02_c02→s03_c01 过期依赖、尾态冲突；只报告不晋升。
5. 下一阶段任何生成前的模型可用性核验、2.5 迁移最小计划、未解决代码缺口及验收条件。
完成后停止，不启动第四阶段，不用“规则写完了”代替实际行为验收。
~~~

## 后续流程修订

**第四阶段：新对话盲验与真实生产。** 新 Agent 读正式 Skill、canonical、精确视频版本、receipts，自主判断 s02_c02 在原项目是否已选、s03_c01 如何起步。若选择 B，先走合法选片与依赖复核；若希望末段仍在空中，评估单次收束重试。任何付费生成前复核 v2.0 的实际可用性；如需 2.5，先单独实现并验收编译及请求，按新模式重新做小样视觉验证。不得把 2.5 的官方多图说明当成适配器已开放。

**第五阶段：成片接缝。** 基于最终选定 s02_c02 的真实尾态审 G1→G2、G2→G3，区分正常切镜和需修复断裂。比较保留原剪辑、剪辑调整、重做组首、剧情过渡镜、桥接；桥接以两个合格端点为前提。记录修改导致的下游复核范围，不要求全部重生。

资料：随附两份阶段报告为项目事实的起点，执行 Agent 应在仓库重核；[Skill 评估指南](https://agentskills.io/skill-creation/evaluating-skills)建议旧版/新版基线、干净上下文、客观断言与人工复核。
