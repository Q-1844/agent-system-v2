0. 本轮名称
==================================================

Scene System V1
Phase S2A — Location Visual Identity + Approved View Bank

本轮只解决一个问题：

如何让一个 Location
拥有稳定、经过真实生成和视觉审查的多视角视觉身份。

目标链路：

Location
+
Spatial Anchors
+
Set Layout
+
LocationView definition
        ↓
Generate Candidate
        ↓
Visual Review
        ↓
Explicit Approval
        ↓
Approved LocationView Reference

本轮仍然：

不接 Agent。
不修改 Director。
不修改 Scene Sub-Agent。
不修改 Shot。
不生成带 SceneState 的剧情状态图。

==================================================
2. 架构边界再次冻结
==================================================

必须继续保持：

Location
= 可复用地点身份

SceneInstance
= 某个 Story Scene 在一个 Location 中的一次剧情发生

SceneState
= 当前剧情时刻的天气、时间、灯光、损坏、摆设、Prop 位置等

LocationView
= 一个稳定空间视角定义

本轮生成的是：

Location Base View

不是：

SceneInstance State View。

因此本轮 LocationView 图片中
不要加入：

特定 Story Scene
暴雨剧情
破窗剧情
人物位置
Prop placement
某一 Shot lighting

除非它本来就是 Location 长期 identity 的一部分。

==================================================
3. LocationView 不是图片
==================================================

必须继续保持：

LocationView
≠ ReferenceAsset

LocationView 是空间视角定义。

例如：

view_id
location_id
label

camera_zone
look_direction
visible_anchor_ids

它回答：

“从哪里往哪里看，
应该看到哪些稳定空间结构？”

ReferenceAsset：

才回答：

“这个 View 当前批准的视觉图是哪一张？”

这两个概念绝对不要合并。

==================================================
5. View Bank 原则
==================================================

正式固化：

Minimum Coverage
+
On-demand Expansion

系统不得要求：

每个 Location 自动生成 8 个方向。

推荐生产原则：

初始 Location 通常只需要：

Hero / Establishing
+
Reverse Coverage
+
1～2 个剧情关键方向

约 2～4 个 approved LocationViews。

以后真的有新 Shot 需要新角度：

再创建新 LocationView
→ Generate
→ Review
→ Approve。

把这个原则写进：

代码注释
报告
测试

不要在 UI/API 里暗藏“generate all directions”。

6. S1 integrity preflight
==================================================

在真正写视觉生成前，

不是重新压力测试整个系统。

B.

引用的 Anchor：

D.

实际上静默覆盖未传字段。

如果这些当前已经有测试：

单独 commit，

==================================================
19. Cross-canonical approval protocol
==================================================

scene_system.json
和
resources.json

是两个 canonical。

不要假装两个 JSON 文件
可以 magically atomic transaction。

Approval 必须设计成诚实的 saga。

建议：

阶段 A：

短锁读取 Scene candidate
验证：

candidate still valid
review evidence still pass
view basis still current

释放。

阶段 B：

通过冻结 Resources service
注册 ReferenceAsset。

阶段 C：

重新获得 project lock
重新读取 Scene View
再次验证 approval basis。

若仍有效：

attach：
LocationView.reference_asset_id = new_ref_id
approval_status = approved

若已经 stale：

绝不 attach。

新建但未绑定的 ReferenceAsset
记录为：

unbound/orphaned approval asset

写入 approval record。

不要偷偷删除，
除非 Resources 已有安全删除机制并能证明零引用。

以后可 GC。

最重要：

不能为了避免 orphan
牺牲 canonical 正确性。
