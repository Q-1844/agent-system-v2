==================================================
0. 本轮目标
==================================================

Phase 1B 只建立 Production Resources 的：

1. typed domain models
2. project-scoped ResourceStore
3. lightweight read service
4. read-only HTTP API
5. legacy Character.views read adapter
6. 完整兼容/持久化/回归测试

本轮不生成图片。
不做视觉 Review。
不做 Shared Library 升级。
不做前端。
不接任何 Agent。

目标是先证明：

“资源数据模型和 canonical storage 本身是稳定的，
并且完全不会扰动现有 Character / Story / Shot / Agent 系统。”

==================================================
1. Phase 1A 结论继续冻结
==================================================

以下架构原则继续成立：

Character = “这个人是谁”
保持现有 Character canonical：

Character {
    name
    description_en
    views
}

不迁移。
不增加 character_id。
不改变 Scene.characters / Shot.characters 的 name-based 引用。

Clothing = 独立服装设计资源。

CharacterLook =
“某个 Character 在某套稳定服装/外观状态下的完整视觉形态”。

Look 必须有独立稳定 look_id。

Prop = typed resource。

ReferenceAsset = Production Resources 使用的统一视觉引用对象。

scope 是资源属性，不是资源类型。

Shared Library ≠ Project 的共同可变对象。

Location 不属于 misc Other。
本阶段不实现 Location。

==================================================
2. 对 Phase 1A 报告的两个实施修正
==================================================

这两个决定以本提示词为准。

-------------------------
修正 A：Phase 1B 不扩展 src/core/models.py 的 Asset
-------------------------

Phase 1A 报告 OPEN Q1 推荐过：

给现有 Asset 增加
asset_id/checksum/source/origin

本轮不要这样做。

原因：

现有 Asset 已经被 Character.views、
ImageAsset、VideoAsset、AudioAsset 等旧系统广泛使用。

给 Asset 增字段可能改变旧对象的序列化输出，
从而无意修改 project.json 和 project signature。

Phase 1B 必须保持：

src/core/models.py::Asset
bit-for-bit 行为不变。

请在：

src/resources/models.py

中新建独立：

ReferenceAsset

它是 Production Resources 域的 typed object。

同时建立只读 adapter，
能够把已有 Character.views 中的 legacy Asset
映射成 ReferenceAsset-compatible read view。

注意：

adapter 只读。
绝不把 legacy views 自动重新写盘。
绝不迁移旧三视图。

-------------------------
修正 B：Phase 1B 不修改 Project dataclass/project.json schema
-------------------------

Phase 1A 报告曾建议把：

looks
clothings
props
reference_assets

additive 写入 project.json。

本轮不要这样做。

建立独立的项目资源 canonical companion store：

projects/{project}/output/resources.json

这是 Production Resources 域的 canonical。

现有：

output/project.json

完全不改变 schema。

不要修改：

Project dataclass
Project.to_dict/from_dict
schema_version=2
migrate_v1_to_v2

理由：

Production Resources 属于生产资产域，
没有必要因为资源模块上线而改变所有旧 Project 的序列化形状、
project_signature 或 workspace revision。

ResourceStore 可以直接复用：

atomic_write_json
project_write_lock

的底层机制，
不需要依赖 ProjectStore 才能获得可靠写盘。

因为现有 Character 没有 character_id，
本阶段禁止改变它。

6. ResourceStore
==================================================

新增：

src/resources/store.py

职责必须非常纯：

load
save
get
list
put/create
update
delete

以及必要的 canonical serialization。

关键要求：

A.
旧项目没有 resources.json 时：

load → 返回空 ResourceDocument

但绝对不能因为一次 read/list
就在磁盘上自动创建 resources.json。

读操作必须零副作用。

B.
第一次真正 resource write 时
才创建 resources.json。

C.
写入必须 atomic。

D.
如果当前项目已有 project_write_lock，
复用同一项目锁，避免 project.json/resources.json
出现并发写时的不可控竞态。

E.
序列化 deterministic。

F.
未知 schema_version 必须 fail closed，
不能静默猜测。

G.
坏 JSON / 缺字段必须给明确错误，
不能偷偷重置为空导致资产丢失。

==================================================
7. revision/OCC
==================================================

本轮不要接 Agent，
但现在就为以后留下稳定 revision 语义。

不要给 project resource 持久化一个
每修改一次 +1 的 version 字段。

对：

resources document
单个 Look
单个 Clothing
单个 Prop

提供 deterministic content fingerprint。

风格与现有 Agent：

expected_revision / sha256 token

一致。

例如 service read 返回：

revision

但 canonical 内不需要持久化这个 derived revision。

Shared Library 的 shared_version
属于以后 Phase 1D，
与这里的 OCC revision 不是同一个概念。

不要混淆二者。

==================================================
8. Legacy Character.views Adapter
==================================================

这是 Phase 1B 很关键的一部分。

现有 Character.views 必须保留。

新增只读 adapter，例如概念上：

legacy_character_references(character_name)

把：

Character.views["front"/"side"/"back"]

映射成统一的 ReferenceAsset-compatible read object。

但是：

不要给这些 legacy view 真正分配并持久化 ref_id。
不要自动创建 CharacterLook。
不要自动创建 Base Look。
不要写 resources.json。

这是 read compatibility view。

它的目标只是证明：

以后 Resources UI / Look Generator
可以用统一方式读取旧 Character 三视图。

如果以后用户明确创建 Base Look，
再生成真正稳定 look_id/ref_id。

不要现在偷偷 materialize。
