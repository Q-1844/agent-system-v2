==================================================
四、必须坚持的核心资源关系
==================================================

这部分是已经冻结的架构原则，不要重新推翻。

-------------------------
A. Character
-------------------------

Character 表示：

“这个人是谁”。

它负责稳定身份。

例如：

Alice

Character Identity 中长期稳定的部分包括：

- name
- identity description
- stable facial/body/hair traits
- existing character references
- lineage/revision
- 后续可能扩展 voice 等

当前仓库已有 Character canonical。

必须优先兼容现有 Character，
而不是先推翻 Character 数据模型重新造一套。

特别调查：

- 当前 Character 存在哪里
- 当前稳定标识到底是什么
- Scene / Shot 怎样引用 Character
- rename 怎样传播
- 三视图怎样存储
- Character Designer 使用哪些工具和 schema
- 哪些地方依赖现有结构

Phase 1 的设计必须避免破坏这些依赖。


-------------------------
B. Clothing
-------------------------

Clothing 是独立、可复用的服装设计资源。

例如：

Black Coat
School Uniform
Police Uniform
Battle Suit

它描述：

“这件衣服是什么样”。

它可以拥有：

- clothing_id
- name
- description
- design traits
- material
- colors
- reference images
- approved reference images
- cover image
- tags
- revision
- origin / lineage
- approval state

但 Clothing 本身不等于：

“Alice 穿上它之后长什么样”。

也不要假定任意 Clothing 可以在 Shot 生成时直接可靠地套到任意 Character。


-------------------------
C. Character Look
-------------------------

这是 Production Resources V1 最核心的新实体之一。

CharacterLook 表示：

“某一个具体 Character 在某一套稳定外观/服装状态下的完整视觉形态”。

例如：

Alice · Base
Alice · School Uniform
Alice · Black Coat
Alice · Battle Suit

数据关系大致应是：

Character
    └── CharacterLook
            ├── optional clothing_resource_id
            ├── appearance description/delta
            └── approved reference bank

例如：

Character = Alice
Clothing = Black Coat

经过组合生成和审核以后：

→ CharacterLook = Alice_Black_Coat

真正进入以后 Shot Reference 系统的，
应该优先是：

look_id

而不是每一次临时使用：

character_id + clothing_id + prompt text


==================================================
五、为什么 Phase 1 必须支持“提前组合 + 生成 + 审查”
==================================================

系统希望把最困难的视觉组合问题提前解决一次。

错误方式：

Shot 001：
Alice + Black Coat → 第一次组合

Shot 002：
Alice + Black Coat → 再组合一次

Shot 003：
Alice + Black Coat → 又重新组合

这样每个 Shot 都承担人物和服装重新组合的风险。

正确目标：

Alice
+
Black Coat
↓
生成 Alice_Black_Coat Look 候选图
↓
视觉检查
↓
批准一组稳定 Reference
↓
之后大量 Shot 直接复用这个 Look

因此 Phase 1 架构必须能够表达完整生命周期：

draft
→ generating
→ candidate
→ reviewed
→ approved / rejected

请调查当前代码里：

- 现有 Character 三视图生成机制
- 通用图片生成客户端
- Asset 落盘机制
- generation receipt
- Visual Review 底层能力
- approval 是否已经有类似机制
- 哪些能力可以复用
- 哪些能力目前只绑定在 Director Agent 内

非常重要：

不要为了 Resource Review 去修改 Director 的现有 tool-loop。

如果现有 Visual Review 中存在可安全复用的底层视觉模型/client/service，
请设计“复用底层能力但不改变 Director 行为”的方案。

如果没有安全复用边界，请明确指出，
不要强行耦合。

不要让每种对象以后各自发明一套图片字段。

候选字段方向包括：

==================================================
八、必须保留并升级“跨项目共用库”
==================================================

历史系统曾经存在一个跨项目的全局角色库，
历史路径可能类似：

saved_characters/

但不要相信历史路径仍然正确。
必须搜索当前真实仓库确认：

1. 它是否仍存在；
2. 后端如何读取/写入；
3. 前端是否还有入口；
4. 它保存什么字段；
5. 三视图/图片如何保存；
6. 是否还有代码依赖；
7. 是否已经废弃；
8. 是否存在迁移风险。

无论实现细节如何，
新的架构必须继续支持：

跨项目复用已经创建过的人物和资源。

但共用库的正确语义不是：

“所有 Project 直接共同修改同一个 Character 对象”。

正确方向应是：

Shared Production Library
        │
        │ import
        ▼
Project Production Resources

Shared Library 是跨项目复用源。

Project Resources 才是当前项目的生产事实。


==================================================
九、Shared Library 必须解决的隔离问题
==================================================

请重点设计以下语义。

假设：

Project A 从 Shared Library 导入 Alice。

随后 Project A 为剧情需要把 Alice 改成：

短发、脸上有伤。

Project B 同时也使用 Shared Alice。

绝对不能因为 Project A 修改，
Project B 自动发生变化。

因此推荐研究并比较：

A. Copy-on-import
B. immutable version reference
C. content-addressed shared media + local metadata snapshot
D. 其它符合当前项目架构的方案

Phase 1 优先：

可靠性 > 节省磁盘。

我当前更倾向：

Shared Resource 是版本化母版；
Import 后得到 Project-local snapshot / instance；
记录来源 lineage；
项目内修改不自动写回 Shared Library。

类似：

project_resource.origin = {
    source: "shared_library",
    shared_resource_id: "...",
    shared_version: "...",
    imported_at: "..."
}

如果 Shared Alice 后来发布 v4：

Project A 不应该自动变成 v4。

最多显示：

update_available

只有显式执行：

Update from Shared Library

以后才发生升级。

同理：

Project → Shared Library

也必须是明确的 Publish / Save to Shared Library 行为。

不能项目内每次修改都偷偷污染共用库。

请结合当前系统结构判断最终实现方式。
