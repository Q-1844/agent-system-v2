```text

+
```

# 8. First-frame temporal rule —— 本阶段最重要规则

对于 **first-frame / initial image generation**：

允许作为当前视觉状态的 ReferenceItem：

```text
temporal_scope = start
temporal_scope = throughout
temporal_scope = static
```

必须排除：

```text
temporal_scope = end
```

这一规则必须先于 `priority`。

也就是说：

```text
priority=primary
+
temporal_scope=end
```

仍然：

```text
不得进入 first-frame current-state reference
```

绝不能因为它是 `primary` 就塞进首帧。

# 9. pick_up 必须保持正确

对于：

```text
Alice picks up Pistol
```

S3B.3 已经规定：

```text
Alice holding Pistol Composition
→ end-state evidence
```

所以 Image / First-frame Adapter 必须：

```text
EXCLUDE:
holding-Pistol Composition as current/start reference

INCLUDE:
Alice Look / start appearance

INCLUDE when supported:
Pistol standalone identity reference

INCLUDE:
Scene reference
```

不得重新犯：

```text
首帧直接给“已经拿着枪”的人物图
```

然后 prompt 又要求：

```text
Alice reaches for / picks up pistol
```

这种相互冲突的输入。

必须专项测试。

# 13. Reference priority 与 temporal 是两个独立维度

必须保持：

```text
priority:
primary
supporting
context
```

和：

```text
temporal_scope:
start
throughout
end
static
```

是两个维度。

正确处理顺序：

### Step 1 — Temporal eligibility

first-frame：

```text
start
throughout
static
```

eligible。

```text
end
```

not eligible。

### Step 2 — Semantic/provider mapping

根据：

```text
purpose
source_type
priority
```

映射到 provider 支持的 reference mechanism。

不要先按 primary 全塞，再看 temporal。

# 14. Provider capability 必须来自真实代码

不要假设 provider：

* 能吃无限图片
* 支持多 Reference
* 有 character slot
* 有 scene slot
* 有 style slot
* 支持 image weight
* 支持 IPAdapter
* 支持 ControlNet
* 支持 firstFrame
* 支持 lastFrame

先读取当前真实 provider API / client。

然后建立一个明确的 capability mapping。

例如，如果当前 provider 只支持 N 张 reference：

必须确定性处理。

推荐规则：

1. temporal 不合格 → 必须排除
2. required primary reference 优先
3. supporting/context 再按 Pack 原始确定性顺序处理
4. 不能表示所有 required primary semantics 时，不得静默随机删除

如果 provider capacity 真的不足以表达必需输入：

```text
BLOCK / ADAPTER_UNSUPPORTED
provider_reference_capacity_insufficient
```

或当前项目等价结构化错误。

不要随机选几张继续生成。

对于只是 optional supporting reference 被容量限制排除：

可以继续，

但必须在 Adapter diagnostics 中明确记录：

```text
dropped_optional_reference
```

# 17. Composition

Composition 的意义是：

```text
visual relationship evidence
```

不是单纯 Character identity。

因此 provider mapping 时必须保留：

```text
purpose=spatial_relation
或
purpose=action_state
```

的语义区别。

不要把：

```text
Composition
```

和：

```text
CharacterLook
```

无差别扁平成“随便几张人物参考图”。

如果 provider API 本身无法表达语义类型：

Adapter 可以转换成 provider 可表达的形式，

但内部 selection / ordering / diagnostics 必须仍然知道它们的语义角色。

# 24. Reference resolve failure policy

如果一个 **required primary** ReferenceItem：

```text
在 Pack 编译时合法
但 Generation resolve 时实际无法得到媒体
```

不得静默继续。

应返回结构化失败，例如：

```text
reference_media_unresolvable
```

并保证 provider 没有被调用。

对于纯 compatibility / optional supporting evidence：

如果当前架构允许降级，

可以：

```text
drop + diagnostic
```

但必须测试并报告。

不要把 required / optional 混在一起。

# 25. Generation 前第二道 race guard

S3B.3 已经保证：

```text
compile 前后没有 mixed-state Pack
```

但 S3C.1 会增加新的时间窗口：

```text
compile Pack
→ resolve reference media
→ build provider request
→ provider call
```

这期间 canonical 仍可能变化。

因此在真正 external provider dispatch 前，

必须执行一次轻量 **pre-dispatch basis guard**。

目的：

> 确认当前 READY validity 仍与刚才 Pack 的 basis 对齐。

至少比较现有 S3B.3 已使用的关键 basis：

```text
binding revision
binding document revision
resolved dependencies
resolved SIV
visual profile fingerprint
readiness
```

尽量复用现有 S3B.2/S3B.3 comparison helper。

不要复制一套新 fingerprint engine。

如果变化：

```text
provider MUST NOT be called
```

返回：

```text
dependency_changed_before_generation
```

或等价结构化错误。

不要：

* auto refresh
* auto rebind
* silently recompile and call
* 使用旧 Pack + 新媒体混合生成

调用者可以显式重试整个 generation。

# 26. 无关 dependency 变化不得误伤

当前 Shot 只用：

```text

```

在：

```text

→ provider dispatch
```

之间修改：

```text

```

只要当前 Shot validity/basis 不变化：

Generation 应继续。

这一步继续证明：

```text

```

而不是全项目大锁。

# 27. Legacy / Unbound compatibility —— 非常重要

不要为了本阶段直接炸掉所有旧项目。

先检查当前真实产品是否仍允许未建立 ShotProductionBinding 的旧 Shot 生成。

建议采用明确双路径：

```text
Shot 已存在 ShotProductionBinding
    ↓
必须走新 Binding-aware generation path
    ↓
READY → compile Pack → Adapter
NOT_READY → BLOCK
    ↓
绝对不能 fallback legacy

Shot 完全没有 Binding
    ↓
如果当前产品仍需要 legacy compatibility
    ↓
保持现有 legacy generation behavior bit-for-bit
```

关键规则：

> **一旦这个 Shot 已经进入 Binding 世界，就不能因为 Binding 出错而偷偷退回 legacy generation。**

否则：

```text
NOT_READY
```

将失去任何意义。

如果当前系统已有更明确的：

```text
LEGACY / UNBOUND / BOUND
```

状态，请复用。

如果真实代码证明旧 generation 已经允许全部切到 fail-closed，也可以这么做，但必须给出证据，不要自行假设。
