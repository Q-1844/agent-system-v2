1. VideoVersion `input_visuals` 记录实际视频输入及 semantic_role；
2. full-story-relay-calibration / keyframes-bridge-repair Skill 已完成 reference / hard boundary / relay boundary 分流，并引入 minor 吸收、major 镜内失败单次重试、尾态偏离插曲制。

本轮不要继续扩展功能，也不要重新设计工作流。

本轮目标只有一个：

> **确认系统事实层、UI 槽位、历史 canonical、下一次 generation dispatch、Skill 决策与 trace 六者之间已经真正语义闭环。**

先诊断，再决定是否需要最小修复。

禁止为了报告 PASS 而修改断言、降低检查标准或增加新的强制状态机。

# 0. 总原则

必须以真实代码和真实 runtime 行为为准，不以 PHASE39E 报告文字自证。

保持当前架构原则：

* System 负责事实、provenance、显示、确定性诊断；
* Skill 负责生产方法和软约束；
* 不新增全局“组状态机”；
* 不把 Group 做成 canonical 强制实体；
* 不新增 Generation Policy Engine；
* 不自动 refresh Binding；
* 不自动 regenerate；
* 不把 reference_only 升格为 hard boundary；
* 不因为 Agent 偶尔不听话就给整个系统增加硬闸门；
* 不修改 Story/Scene 来迎合生成结果；
* 不破坏现有 legacy / UNBOUND 路径。

所有问题按：

`CONFIRMED BUG / DESIGN GAP / EXPECTED BEHAVIOR / TEST GAP`

分类。

只有 CONFIRMED BUG 或明确 DESIGN GAP 才允许做最小修复。

# 1. 第一优先级：检查“首帧槽同步”是否污染下一次生成

这是本轮最高优先级。

当前 `_sync_first_frame_slot` 会在视频完成后，把：

* `relay_start_boundary`
* `reference_only + source=prev_tail`

同步进入 Shot 首帧槽。

必须回答：

> 这个同步到底只是“为了让用户看到事实”，还是会改变下一次视频 generation dispatch？

建立至少以下真实/确定性测试。

## Case A — reference_only → rerun

构造一个 Group Root Shot：

* generation mode = multi/reference-only；
* 实际 provider 只消费 reference image；
* reference 不是 hard first frame；
* 视频生成成功；
* 系统把关键 reference 显示/同步到槽位。

然后**不手工清槽**，直接重新生成同一 Shot。

必须截获第二次真正发送给 provider 的 request。

PASS 条件：

* 第二次仍是 reference-only / multi 语义；
* slot 中存在图片不能让 mode 偷偷变 i2v；
* slot 图片不能自动成为 `image_url = hard frame 0`；
* provider request 必须与 Agent 本轮明确选择的 generation mode 一致。

如果第二次因为 UI/canonical 同步而把 reference 当 hard first frame：

`BLOCKER — display state polluted generation state`

必须修。

---

## Case B — relay boundary → rerun

Shot B：

* Shot A 已有 selected VideoVersion；
* B 从 A 的真实 `video_end_frame` 接力；
* B 生成成功；
* B 首帧槽同步为 A 的真实尾帧。

再次生成 B。

PASS：

* opening boundary 仍由 relay semantics / source_version 决定；
* 不允许仅因为本镜首帧槽已有图片，就退化成普通 i2v hard_start；
* semantic_role 仍为 relay_start_boundary；
* 不允许生成新的 storyboard first-frame 覆盖 relay。

---

## Case C — reference-only prev_tail

单独构造：

* 上镜尾帧作为 reference_only；
* 明确不是 hard relay boundary。

生成完成后系统允许把该图显示进槽，并标记 `[参考]`。

再次生成。

PASS：

* 它依然只是 reference；
* 不得因为已经进入“首帧槽”而变成 hard boundary。

这是最容易出现 reference → boundary 语义污染的 Case，必须单独测试。

# 2. `input_visuals` 必须对账真实 Provider Dispatch

当前不要只检查 adapter 的 `semantic_roles`。

我要验证：

> `input_visuals` = provider 实际收到的图片输入事实。

在 provider dispatch 最后一层做 capture / spy。

至少覆盖：

* multi/reference-only；
* i2v hard_start；
* keyframes hard_start + hard_end；
* inherit/relay；
* reference-only prev_tail；
* CharacterLook reference；
* Scene/Prop/Composition reference（如果真实 mode 支持）。

对每个 VideoVersion 输出：

```text
adapter planned visuals
final provider payload visuals
persisted VideoVersion.input_visuals
```

逐项比较：

* URL / asset identity；
* slot；
* 顺序；
* semantic_role；
* source_type；
* source_shot_id；
* source_version（若适用）。

要求给出机器可验证断言。

若 adapter 后面还有过滤、drop、fallback、URL 替换、顺序改变：

`input_visuals` 必须反映最终 dispatch，而不能只反映 adapter 意图。

如果现有 adapter output 已与最终 request 一一对应，则用测试证明，不必改架构。

legacy / resume 无法恢复历史事实时允许空，但必须明确：

```text
provenance incomplete / unknown
```

不得把“未知”写成“没有输入”。

同时检查 `mode_mismatch_warning`：

如果 input provenance 不完整，不允许根据缺失数据产生假的 mode mismatch。

# 3. Relay 必须继续保持 source_version freshness

回查现有 Golden Path 的 relay contract。

真实不变量应继续是：

```text
prev selected VideoVersion
→ its real video_end_frame
→ source_version = selected VideoVersion identity
→ next shot relay
```

不得退化成：

```text
find a local PNG
→ copy into slot
→ assume it is current prev tail
```

测试：

1. A 生成 VideoVersion V1；
2. B relay V1；
3. B slot 正确显示 A/V1 tail；
4. A 再生成 V2 并切为 selected；
5. 不重新生成 B；
6. 检查 B continuity / slot provenance / source_version。

正确行为必须诚实表达：

* B 当前引用 V1；
* A 当前 selected 已是 V2；
* relay stale 或对应既有 freshness verdict；
* 不允许悄悄把 B 的历史 VideoVersion `input_visuals` 改写成 V2；
* 也不允许 UI 伪装成 B 当初就是用 V2 生成的。

历史 VideoVersion 的 `input_visuals` 是 immutable provenance。

如果用户之后重新生成 B：

新 VideoVersion 才记录 V2。

当前需要亲自检查 Workbench，而不是只看 JSON。

### A. 用户理解的首/尾帧槽

不要做大 UI 重构。

目的只是保证：

> 用户只看大槽位，也不会再次把 reference_only 误解成 frame 0。

# 5. 修正 Group 的定义层级，但不要做系统强制

检查当前 Skill 中所有：

```text
段 = 组
```

类似绝对措辞。

改成更准确的软语义：

> Story segment / Scene 可以作为默认分组提示，但 Group 的真实连续性语义由镜头间是否承接上一条真实 `video_end_frame` 决定。

因此：

```text
same segment + relay
→ same continuity group

same segment + intentional_cut
→ 可以开始新 group

new segment + explicit relay
→ 技术上仍允许连续 group

new segment + new reference/hard start
→ 新 group
```

系统层不要存 group canonical，不要阻断任何合法情况。

`relay_intent_hint` 仍然只是 soft hint。

`continuity_type=intentional_cut` / `reference_only_note` 仍然可以解释豁免。

# 6. 检查 trace soft warning 的“完全缺失”盲区

当前三条 warning 不要改成硬闸门。

但必须测试一种情况：

```text
视频已经生成完成
Agent 完全没有调用 trace_upsert
```

现在系统会发生什么？

如果答案是：

```text
完全没有任何机会发现
```

不要在全局 Runtime 增加强制 hook。

优先采用 Skill-local 收尾动作：

```text
在 full-story-relay-calibration 即将结束当前 Shot 前
→ read 当前 Shot trace
→ 若本次 VideoVersion 尚无 adjudication
→ Agent 自己补做 review/adjudication/trace
```

Producer 最终汇报时同样必须读取 trace 事实，而不是引用 Director prose。

这是 Skill workflow self-check，不是系统强制状态机。

验证：

* 完整 trace → 无噪音；
* trace 缺 human_deviation_level → warning；
* trace 完全不存在 → Skill 自检能发现；
* 未使用该 Skill 的普通 Director 操作 → 零 warning、零干扰。

# 9. Bridge 与 intentional cut 再补一条负面约束

当前“跨 Location”不要自动等于 bridge。

Skill 中明确：

> Bridge 的前提不是“画面差得大”，而是“两端都必须保留并且业务上要求连续过渡”。

因此：

```text
intentional cut
new group
deliberate location jump
montage cut
```

默认不是 bridge repair。

只有：

```text
A endpoint 必须保留
+
B endpoint 必须保留
+
它们业务上必须连续
```

才进入 keyframes bridge。

保留现有双端证据、10s 起步、中间节拍、seed 后禁止 refresh 等纪律。

# 13. 修复纪律

如果所有 P0 项都 PASS：

不要为了“看起来做了事情”继续改代码。
