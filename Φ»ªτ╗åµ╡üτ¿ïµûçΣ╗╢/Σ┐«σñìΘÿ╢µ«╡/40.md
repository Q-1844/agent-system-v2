# 一、这轮真正的目标

当前系统已经完成多个专业 Agent，并且各 Agent 基本拥有自己专业域所需的读取、修改、生成、Review 等 Tool/Capability。

目前暴露出的主要问题不是：

“Agent 没有工具。”

而是：

“Agent 虽然拥有工具，却不稳定地知道面对某类复杂生产任务时应该采用什么方法、按照什么顺序工作、什么时候检查、什么时候修复、什么时候交给其他 Agent、什么时候停止。”

此前我们曾尝试把较复杂的生产协作方法直接写进各 Agent System Prompt。

实际测试表明：

* 底层 production system 本身具有较强能力；
* 使用 zcode / 明确脚本直接编排这些能力时，效果明显较好；
* 让项目 Agent 仅依赖当前 System Prompt 自主完成同样复杂协作时，表现明显下降；
* 因此现在暂停继续堆叠 System Prompt；
* 本轮优先建设正式的 **Skill System V1**。

最终希望形成：

Runtime Invariants
↓
Agent Base System
↓
Skill Discovery / Routing
↓
Skill Runtime
↓
Skill Package
↓
Tools / Compound Tools
↓
Production System

其中：

**System Prompt 负责“我是谁、我拥有什么权限、哪些事实可信、什么时候应该寻找/加载 Skill”。**

**Skill 负责“这一类事情应该怎样做”。**

**Tool 负责“执行具体动作”。**

**Compound Tool / Runtime 负责必须确定执行、不能依赖 LLM 记住顺序的机械流程和硬约束。**

不要再把复杂 workflow 当成越来越长的 System Prompt。

# 三、核心架构原则

本轮目标不是简单建立：

agent_a/skills/
agent_b/skills/
agent_c/skills/

也不是让所有 Agent 永远看到所有 Skill。

优先设计为：

**一个 Canonical Skill Registry + Agent-specific Skill Bindings / Views + Progressive Disclosure。**

概念上：

Shared Skill Registry
↓
Skill Packages
↓
AgentSkillBinding
↓
Agent-specific Skill Catalog / View
↓
Skill Discovery
↓
Load selected Skill
↓
Execution

同一个 Skill 原则上只存在一个 canonical package。

不同 Agent 通过 Binding 获得：

* 是否可见
* 在该 Skill 中的角色
* routing priority
* authority/trust tier
* activation policy
* role-specific instructions/resources

不要为了不同 Agent 复制五份相同 workflow。

如果你调查当前代码后发现更自然、更简单且能满足这些语义的实现方式，可以调整具体类名、文件结构和内部实现。

**不要为了匹配本文示例而破坏现有项目架构。**

# 四、Skill System V1 必须解决的核心对象

请根据当前代码设计最小但可长期扩展的模型。

至少需要表达两个不同概念：

## SkillPackage

表达 Skill 本身。

建议考虑：

* skill_id
* version
* name
* description
* category
* source
* status
* compatibility
* required_capabilities
* optional dependencies
* trigger / applicability metadata
* package resources
* entry instructions

不要过度 schema 化自然语言工作方法。

Skill 的主体仍然应该允许使用 Markdown / 文本资源表达复杂生产知识。

## AgentSkillBinding

表达：

“某一个 Agent 与某一个 Skill 的关系。”

至少应能表达：

* agent_id
* skill_id
* enabled
* role
* routing_priority
* authority_tier / trust tier
* activation_mode
* role-specific resource / instructions（如果需要）

特别注意：

**Skill 的重要程度不是 Skill 的绝对属性，而是 Agent × Skill 的关系。**

例如同一个 continuity workflow：

Producer 可能是 coordinator；
Director 可能是 primary executor；
Script Writer 可能是 contributor；
Character Designer 可能只在 identity drift 时参与。

不要用一个全局 priority 抹平这些差异。

# 五、routing priority 与 authority 必须分开

不要把：

“这个 Skill 多容易被选择”

和：

“Skill 冲突时谁拥有更高权威”

做成同一个数字。

至少在语义上分开：

# routing_priority

Skill selection / ranking

# authority_tier

instruction conflict resolution

用户未来上传的 Skill 可以非常匹配当前任务，因此可以被主动选择；

但它不能因此覆盖：

* System Prompt
* Agent ownership
* explicit user instruction
* canonical truth
* OCC
* permissions
* approval
* truth gates
* production safety invariants
* built-in core workflow 的硬约束

本轮请把这个边界设计清楚。

# 六、Skill 分类不要过度设计

V1 不要建立几十种分类。

建议从少量稳定类别开始，例如：

* workflow
* domain
* situation
* review_recovery

其中当前最重要的是：

**workflow**

因为我们现在首先要迁移的是已经真实测试过的复杂生产协作方法。

source/trust 与 category 不要混为一谈。

例如未来：

category = situation
source = user_upload

完全合法。

# 七、Progressive Disclosure 是本轮核心要求

Skill System 的目的之一，就是不要让每个 Agent 每轮背完整技能库。

因此请实现清晰的分层加载。

理想语义：

L0 — Agent Base System
永远存在：
Role / Ownership / Authority / Truth Discipline / Tool usage / Generic Skill Policy

L1 — Skill Catalog Metadata
Agent 只看到自己可用 Skill 的少量 metadata，例如：
name / concise description / trigger / priority

L2 — Selected Skill Instructions
真正判断相关以后，才加载 Skill 主体。

L3 — Supporting Resources
只有 Skill 执行需要时，再加载 role-specific reference、examples、failure guide 等。

不要在 System Prompt 中把所有 SKILL.md 全部展开。

也不要让 Agent 每轮扫描整个磁盘 Skill 目录。

Skill discovery 应该廉价、确定、可追踪。

---

# 八、System Prompt 本轮要做“减法”，但不要过早删除

当前各 Agent System Prompt 中可能已经包含我们此前为了两个协作模式加入的大量 workflow instruction。

不要一开始就删除。

正确顺序：

1. 找出哪些属于永久 Agent identity / ownership / truth discipline；
2. 找出哪些实际上属于 workflow knowledge；
3. 建立 Skill Runtime；
4. 将 workflow 内容迁移为 Skill；
5. 确认 Agent 能正确 discover/load；
6. 再从 System Prompt 删除重复 workflow 内容。

最终 Agent Base System 应主要保留：

* Role
* Ownership
* Domain Authority
* Autonomy boundary
* Truth discipline
* Tool usage fundamentals
* Skill discovery / loading policy
* delegation fundamentals

而不是保存某一个具体生产 workflow 的几十条步骤。

# 九、第一批不要做十几个 Skill

Skill System V1 基础完成以后，只迁移我们已经拥有真实证据的生产方法。

第一批 Golden Skill 聚焦目前这两个已经经过人工/脚本生产实证的协作模式。

请从现有规格、当前 Prompt 和真实 production code 中确认它们的准确边界，不要凭本文重新发明。

重点涉及：

* relay / tail-frame continuity
* adaptive calibration
* seam measurement
* visual review
* none / minor / major classification
* repair / cascade
* boundary handling
* keyframe / bridge strategy
* validation
* recovery
* 多 Agent handoff

是否最终表现为：

一个大的 workflow Skill + bridge strategy resource

还是：

两个相互关联的 workflow Skills

请你在读完当前代码和真实阶段资料后判断。

不要为了形式强行拆 Skill。

如果 bridge 本质上只是 continuity workflow 的 repair strategy，就保持它为 supporting resource / sub-protocol。

# 十一、Skill 不能变成隐藏的新权限系统

这是硬约束。

**Skill 只教 Agent 如何使用它已经拥有的能力。**

Skill 不得：

* 新增 Tool permission；
* 绕过 Agent ownership；
* 绕过 OCC；
* 绕过 revision；
* 绕过 approval；
* 绕过 truth gate；
* 直接修改其他 Agent 专属 canonical；
* 绕过正式 production service；
* 通过 shell/script 偷偷完成生产动作。

如果 Skill 声称需要某 capability，而当前 Agent 没有：

必须明确 fail / delegate / request appropriate owner。

不能因为 Skill 写着“执行 X”就获得 X 权限。

# 十二、LLM 决策与机械执行必须分层

不要把 Prompt / Skill 当程序代码。

以下类型逻辑适合 Skill：

* 判断当前属于什么生产情境；
* 选择 workflow；
* 判断什么时候 review；
* 根据 review/measurement 选择 repair strategy；
* 判断是否需要协作 Agent；
* 判断何时停止、升级、重新计划。

以下类型逻辑如果要求严格顺序、原子性、确定执行，则优先放：

Tool / Compound Tool / Runtime

例如：

* OCC
* revision validation
* atomic write
* deterministic seam measurement
* trace persistence
* boundary extraction
* 固定顺序的一组 mutation
* 必须保证完整执行的 bridge mechanical operation

先审计当前是否已经存在对应 Tool。

**已有能力不要重复实现。**

只有真实缺失且是 Skill 执行所必需的 capability，才允许补最小 Tool/Compound Tool。

* 哪个 Skill/version 被加载？
* 哪个 Agent 以什么 role 使用？
* 加载了哪些 supporting resources？

* 在哪里失败？
* 调用了哪些 tools？
* 是否发生 delegation / handoff？
* 最终 completion / failure reason 是什么？

不要把完整 chain-of-thought 持久化。

我们需要的是结构化 execution trace / decision evidence，而不是模型私有推理文本。

日志必须足以支持以后：

vs
Skill V1

# 十五、测试策略——这一轮先测 Skill System，不急着证明视频效果

这点非常重要。

当前 Agent 测试效果已经明显弱于直接脚本驱动。

因此不要一上来又烧大量真实视频试图“调 Prompt 调到成功”。

本轮测试分层：

### Phase A — Architecture / Unit

验证：

* registry
* package validation
* binding
* per-agent filtering
* priority
* authority
* version
* enable/disable
* invalid package fail closed
* capability dependency
* progressive loading
* trace
* user-extension trust boundary

### Phase B — Skill Discovery

构造明确任务，验证：

* 无关任务不加载 continuity Skill；
* continuity 任务能够找到正确 Skill；
* Agent 只看到属于自己的 Skill view；

### Phase C — Workflow Dry Run / Mock

* Agent handoff；
* none/minor/major；
* repair decision；
* bridge decision；
* failure recovery；
* major stop / escalation；

### Phase D — Golden Replay

本轮不要把“视频模型随机生成质量”与“Skill Runtime 是否正确”混成一个指标。

# 最后一个原则

这轮工作的成功标准不是：

“把原 System Prompt 搬进几个 Markdown 文件。”

真正成功应该是：

**Agent 的身份和权限保持稳定；生产方法变成可发现、可加载、可版本化、可测试、可观察、可替换的 Skill；复杂生产知识以后可以持续演进，而不需要不断重写 Agent 本身。**

先调查，后设计；先证明基础设施，再迁移 workflow；先做 deterministic / mock 验证，再花真实生成资源。

发现当前假设与代码事实冲突时，以代码和真实执行证据为准，并清楚记录原因。
