==================================================
4. 所有写操作必须使用 OCC
==================================================

使用 Phase 1B 已经实现的：

document_revision
look_revision
clothing_revision
reference_asset_revision

等 deterministic fingerprint。

规则：

更新/删除单个资源：
expected_revision = 当前 resource revision

创建新资源：
expected_revision = 当前 ResourceDocument revision

stale 时：

不写入。

返回结构化：

{
  ok: false,
  error: "stale_revision",
  expected_revision: "...",
  current_revision: "...",
  current: ...
}

不要自动替调用者替换成新 revision。

不要 silent retry。

==================================================
5. project_write_lock 是硬规则
==================================================

任何：

load
→ validate
→ mutate
→ save

必须发生在：

async with project_write_lock(project_name):

的短临界区。

但是：

绝对不能在锁内等待图片模型。

正确模式：

阶段 1：
短锁
读取 + 验证 + snapshot generation basis
释放锁

阶段 2：
无锁
调用图片模型

阶段 3：
重新加短锁
重新读取
验证 generation basis 是否仍然成立
若成立才 commit generated assets
否则拒绝 attach

不能：

拿着 project_write_lock
等几十秒图片生成。

==================================================
19. generation commit 的 stale basis 保护
==================================================

这是本阶段最关键的可靠性机制之一。

场景：

T0：
Look = Alice + Black Coat v1
开始生成。

生成花 30 秒。

这 30 秒内：
用户把 Look 改成 Red Coat
或者 Clothing 被修改。

图片回来后：

绝对不能把旧生成结果
无条件 attach 到新的 Look。

因此：

生成开始前 snapshot：

look_revision
clothing_revision
character identity/reference basis

生成结束后重新加锁。

重新计算 basis。

如果任何关键 basis 变化：

不要 attach candidate 到 Look。

返回：

stale_generation_basis

generation record 仍然诚实记录：
生成完成，但 canonical commit 被拒绝。

输出图片可以保留在 generation_id 临时目录
供诊断，
但不能成为 Look.reference_asset_ids。

绝对不要 runtime 偷偷替换 basis
然后强行提交。
