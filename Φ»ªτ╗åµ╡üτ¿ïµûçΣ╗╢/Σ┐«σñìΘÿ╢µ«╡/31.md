# 1. 当前架构意图

现有架构中应当保持以下职责分离：

## Creative canonical

Shot / Story Scene：

负责镜头创作意图。

例如：

* description
* composition
* shot size
* camera
* action
* opening/end state
* dialogue
* characters

不要把 Production Resource 图片路径塞回 Shot canonical。

## Production binding

`ShotProductionBinding`

负责回答：

**这个 Shot 实际生产时应该使用哪个 SceneInstance、哪个 CharacterLook、哪个 Prop、哪个 Composition。**

Binding 存语义 ID，不存图片路径。

## Validity

`ShotBindingValidity`

负责回答：

**这些绑定现在是否仍然有效、approved、fresh。**

READY / NOT_READY / UNBOUND 是生成前的事实 Gate。

不要在 generation adapter 中重新实现第二套 freshness 判断。

## Reference Pack

`ShotReferencePack`

负责把当前 READY binding 编译成一次生成可以消费的确定性 production context。

它是：

* derived
* ephemeral
* read-only
* 不落盘
* 不成为新的 canonical

它描述 scene / characters / props / action / style / references / temporal semantics。

## Provider Adapter

本轮真正缺的层应该是：

`ShotReferencePack`
→ `Generation Adapter`
→ 当前真实 image/video provider

Adapter 的职责是：

**把模型无关的 ReferencePack 编译成某个 provider 真正支持的输入。**

不要反过来污染 ReferencePack，让 ReferencePack 变成 Agnes 专属结构。

# 2. 本轮第一阶段：完整 Generation Path Audit

在写代码前，先回答下面这些问题，并把调查结果记录下来。

## A. First Frame

找到当前真正执行 first-frame generation 的唯一/主要 handler。

逐行确认：

* prompt 从哪里来；
* style 从哪里来；
* character refs 从哪里来；
* continuity refs 从哪里来；
* reference image 最终是什么结构；
* provider 支持几张 reference；
* reference 顺序有没有语义；
* provider 是否支持 image-to-image / multi-image conditioning；
* generated candidates 如何落盘；
* ImageBatch 保存哪些 provenance；
* char_ref_snapshot 当前如何产生；
* Director / autopilot / HTTP 是否最终汇合到同一个 handler。

## B. Last Frame

同样完整追踪。

特别确认：

* opening/first frame 是否作为 reference；
* continuity reference 是否存在；
* Character / Scene / Prop reference 当前是否缺失；
* ReferencePack 接入后是否会造成 reference budget 冲突。

## C. Video

追踪：

Shot
→ selected first/last frame
→ video prompt
→ provider。

确认当前 video provider 到底支持：

* first frame
* last frame
* reference image
* character reference
* image sequence
* video reference
* 还是仅 prompt + frame

不要假设 provider 能接受 ReferencePack 中所有图片。

# 3. 不要直接把所有 ReferencePack 图片扔给模型

这是本轮最重要的设计要求之一。

Production system 的责任不是“图片越多越一致”。

需要实现一个明确的：

**Generation Reference Adapter / Reference Budget Compiler**

它应该根据：

1. generation type：

   * first_frame
   * last_frame
   * video

2. provider capability

3. ReferenceItem：

   * source_type
   * purpose
   * priority
   * temporal_scope
   * subject_character
   * prop_id
   * relation
   * anchor

决定：

* 哪些图片真正送给模型；
* 顺序是什么；
* 哪些只能转成 prompt semantics；
* 哪些因为 budget 被省略；
* 为什么省略。

禁止简单：

`references = pack.references`

然后全部发送。

---

# 4. Reference 优先级需要从生产语义推导

不要写死成“scene > character > prop”这种过度简单的全局规则。

需要结合 generation stage。

例如 first frame：

通常更关注：

* SceneInstanceView / environment state
* start-state Character appearance
* start-state Composition
* relevant Prop identity

而 pick_up 这种 action：

* end-state holding composition 不应该污染 first-frame start state；
* Character Look 可以是 start primary；
* standalone Prop 可以帮助确认道具身份。

Last frame 则可能相反：

* end-state composition 的价值更高。

Video：

如果 provider 只接受首尾帧，那么 ReferencePack 很多信息应该进入 prompt，而不是额外图片。

如果 provider支持额外 reference，再根据能力适配。

这里必须消费 S3B.3 已经计算好的：

* `priority`
* `purpose`
* `temporal_scope`

不要重新从 action 文本猜一遍。

---

# 5. Scene Reference

对于 READY bound shot：

Scene visual identity / state 应来自：

resolved `SceneInstanceView`

而不是：

* Scene.location 自由文本
* legacy background guess
* Director 自己重新想一个背景

SceneInstanceView reference 是 approved production fact。

但：

不要把 Scene System canonical 复制进 Shot。

通过 ReferencePack / adapter 消费。

如果 scene reference 不存在、revoked、stale：

应该由 Binding Validity 阻止生成。

不要 silent fallback。

---

# 6. Character

Character 需要明确区分三层：

1. Character identity
2. CharacterLook / appearance
3. Composition / spatial relation

不要把三者重新压成一张“角色参考图”。

ReferencePack 已经提供这些语义。

Adapter 应根据 provider 能力决定：

* identity supporting ref
* Look primary/supporting ref
* Composition plate
* 哪些送图片
* 哪些编译为 prompt

如果 Composition 已经包含 Character + Prop 空间关系：

不要同时把它错误地当作普通 identity image。

也不要让 standalone prop reference 覆盖 Composition 所表达的 relation truth。

---

# 7. Prop

Prop reference 的主要意义是 identity。

relation / anchor / interaction semantics 来自：

* Binding
* Composition
* Action

不要让单独 Prop 图片承担空间关系真相。

如果模型 reference budget 不足：

Prop 可以降级成：

* approved identity ref 被省略
* 但 prop semantic description 仍编译进 prompt

必须记录 diagnostics。

---

# 8. Project Visual Profile

BOUND generation 必须消费 ProjectVisualProfile。

不要回落到 legacy StyleAnchor。

UNBOUND legacy generation 暂时保持旧行为。

也就是说必须明确区分：

### UNBOUND

保持现有 legacy generation 行为。

本轮不要为了“统一”破坏老项目。

### BOUND + READY

走新的 Production Generation path。

### BOUND + NOT_READY

fail closed。

不要偷偷 fallback 到 legacy refs。

否则 Binding Validity 就失去意义。

---

# 9. Prompt Compilation

不要把 ReferencePack JSON 原样塞进 prompt。

实现一个 deterministic generation prompt compiler。

推荐结构类似：

PROJECT STYLE

SCENE / ENVIRONMENT

CHARACTERS

PROPS

ACTION / TEMPORAL STATE

CAMERA / COMPOSITION

CONTINUITY

PRESERVE

NEGATIVE / DO NOT CHANGE

但最终结构必须根据当前 provider 和现有 prompt pipeline 调查后决定。

要求：

* deterministic；
* 同输入得到同输出；
* 不调用 LLM；
* 不重新解释 canonical；
* 不复制巨大 JSON；
* 不重复已有 prompt builder 能正确负责的 creative semantics。

核心原则：

**creative prompt + production facts**

而不是用 production facts 替代 Shot 创作意图。

建议形态可以是：

`GenerationRequest`

例如概念上：

* prompt
* negative_prompt
* reference_inputs[]
* first_frame
* last_frame
* ratio
* seed
* model
* diagnostics
* provenance

Reference input 可以具有：

* asset_id
* semantic_role

* source

但不要把 provider-specific request schema 写进 canonical。

然后：

GenerationRequest
→ Agnes adapter
→ Agnes client

未来 CodeBuddy / Kling / Runway / 其他模型才可以增加 adapter，而不用改 Binding / Pack。

这也是本轮必须验证的架构价值。

# 11. Reference Asset Resolution

ReferencePack 只应包含 asset ID，不包含 raw path。

Provider adapter 最后阶段才 resolve：

ReferenceAsset ID
→ ResourceStore
→ local/url
→ provider 所需 data URI / URL / upload form

要求：

* resolution fail closed；
* local 文件必须真实存在；
* 不从 filename 猜语义；
* 不在 canonical 保存 base64；
* checksum/provenance 能记录则记录；
* provider 调用期间不要持 project write lock。

# 13. Race / OCC / stale generation

Generation 通常是：

阶段 1：
短锁读取 + validity + compile basis

阶段 2：
释放锁，调用 provider

阶段 3：
短锁重新验证

必须调查当前 Shot generation 的 concurrency contract。

对于 BOUND generation：

provider 返回以后，在 commit candidate 前必须确认关键 production basis 没有变化。

至少考虑：

* Binding 被 replace/delete
* Look 被更新/revoke
* Composition 更新
* Prop 更新
* SceneInstanceView 重新生成/重新批准/stale
* ProjectVisualProfile 改变

不要长时间持锁等待模型。

如果 basis 变化：

不要把旧结果假装成当前有效 candidate。

可以保留文件作为 diagnostic artifact，但 canonical commit 必须诚实。

尽量复用已有：

* binding revision
* validity
* fingerprint
* generation basis

不要发明 whole-project hash。

# 21. 工作方式

不要一次性大改。

先实现 provider-neutral compilation + reference adapter。

### Phase D — Shot generation integration

接 first frame。

### Phase E — Real E2E

真实生成图片。

不要在前一阶段失败时机械继续下一阶段。

# 23. 最重要的验收标准

本轮真正要证明的不是：

“ReferencePack 能转成一个 JSON。”

而是：

**一个 READY Shot 的 Production Binding，能够把项目已经批准的角色外观、场景状态、道具、空间关系和项目视觉风格，经过可审计、确定性、模型适配的链路，真正送进图片/视频生成模型，并且生成结果明显受到这些 production facts 的约束。**

同时必须证明：

* stale 输入不能偷偷生成；
* unapproved 输入不能偷偷生成；
* legacy unbound Shot 不被破坏；
* provider-specific 细节没有反向污染 canonical；
* 一次生成究竟用了什么 reference 可以被完整追溯；
* 生成过程中 canonical 改变时不会把旧 basis 的结果冒充成当前结果。

先调查真实代码。

不要直接开始写。

调查完成后先给出 Phase A Audit + Phase B 最小实施设计；确认没有隐藏架构冲突后，再继续实现。
