## §1 背景与诊断结论（已发生的事实，详见 PROGRESS §九）

1. 2026-09-23 13:24 起 `i.ibb.co` 在中国线路被 **SNI 级域名阻断**（同 IP 换 SNI=api.imgbb.com
   即通；TLS 握手被杀；任意新旧对象全灭；连上传 key 都被 imgbb 拒 `Invalid API v1 key`）。
   非宕机、非我方回归；Agnes 侧自述抓图 `Read timed out (timeout=30)`。
2. **架构约束（AGNES_API_FACTS §3.3）**：Agnes 视频接口只吃公网 URL，不支持 base64 →
   本地处理的图（末帧/裁剪首帧/抠图）必须经图床。图片接口支持 data URI b64（不受影响）。
3. **今晚实证的替代路径**：GitHub Pages。实测数据：
   - `raw.githubusercontent.com` 仅 **2/10** 可达 → **弃用 Raw，用 `<owner>.github.io`**（3/3 立即应答）
   - 1280×704 尾帧 PNG ≈1MB：晚高峰吞吐 ~33KB/s → **30.5s 撞 Agnes 30s 抓图超时**
   - **JPEG q88 = 168KB（1/6），5 连验收全过（200/image/jpeg/全量字节/1.6–8.0s）**
     ← 仅末帧业务转 JPEG；首帧/资源图保持原格式（见 §4.3，保真要求）
   - Pages 构建延迟 ~40s → 上传后必须**轮询到 200 才算就绪**
   - s06/s07 真实生成成功 = Agnes 服务端实抓 Pages URL 端到端实证
4. 仓库：`Q-1844/agnes-frame-host`（公开，Pages 已启用，deploy from main /root）。
   已在档测试样本：`frames/s05_end_1175fcc8.jpg`、`frames/s06_end_ab78798e.jpg`
   （旧命名，测试期产物，不迁移；新 Host 用 §4.1 的 `objects/` 新命名）。

## §4 设计

### 4.1 GithubPagesHost（src/core/image_host.py 新增，~90 行）——纯托管层

- **MIME 无关**：传进什么 bytes/扩展名，就托管什么。绝不在 Host 内做格式转换
  （JPEG q88 只存在于 §4.3 末帧业务；首帧与资源图原样字节托管——首帧是 i2v 像素锚、
  rehost 承诺 100% 保真）。
- 上传：`PUT /repos/{owner}/{repo}/contents/{path}`，body=`{"message","content"(base64),"branch"}`；
  **新文件无需 sha**（内容寻址唯一命名保证）。PUT 返回 201 即上传成功。
- **路径**：`objects/{sha256_hex16}.{真实扩展名}`——64-bit 内容哈希（设计目标数千张，
  8 hex=32bit 不够）；扩展名取自输入 MIME 推断（image/png→.png，image/jpeg→.jpg）。
  不使用 frames/ 旧前缀（测试期两件样本留在原处，不迁移）。
- **409 处理（幂等）**：409=Conflict，语义不保证「已存在」。收到 409 后：
  1. `GET /repos/{owner}/{repo}/contents/{path}`（带 branch）；
  2. 若文件存在：**解码返回的 base64 字节，计算 sha256 与本地字节对比**（⚠️ 不能直接比
     GET 返回的 `sha` 字段——那是 git blob sha=`sha1("blob <len>\0"+内容)`，与 sha256 不同）；
     匹配 → 幂等成功返回 URL；
  3. 不存在/不匹配 → 视为真冲突，退避重试 PUT ×2（2s/4s），仍失败 fail-loud。
- **并发串行锁**：模块级 `asyncio.Lock`（单后端进程内 4 个入口可能并发上传；
  驱动脚本走 REST，仍经本进程，锁覆盖全部路径）。锁粒度=同 repo 的 PUT 序列。
- 返回 URL：`https://{owner}.github.io/{repo}/{path}`（**不是** raw.githubusercontent.com，
  不是 github.com/blob 网页址）。
- **就绪轮询**：上传成功后 bounded poll GET 返回 URL 直到 200（间隔 5s，上限 180s；
  Pages 构建实测 ~40s）；超时抛错 fail-loud（沿用 ImgbbHost「不静默回落」纪律）。
  轮询超时**不算上传失败**（PUT 已成功），异常需带「URL 已建、Pages 未构建完」语义，
  调用方可重试轮询。
- 重试：PUT/GET 对 5xx/网络错重试 ×3 指数退避（2s/4s/8s）——实测 github.com 路由有抖动
  （curl 000×3 的同一分钟 git push 成功），重试是必要的。
- 鉴权：`Authorization: Bearer ${GITHUB_TOKEN}`；token 放 `.env`（已在 gitignore），
  config 用既有 `${...}` env 替换机制（同 AGNES_API_KEY）。
- **Token：fine-grained PAT**——只授权 `agnes-frame-host` 一个仓库 + **Contents: Read and write**
  （不用 classic repo scope：公开图床仓库没必要给账户级全仓库权限；token 泄露影响面=单仓库）。

### 4.2 config（config/config.yaml）

```yaml
image_host:
  kind: "github_pages"          # imgbb 保留可一键切回
  github_pages:
    owner: "Q-1844"
    repo: "agnes-frame-host"
    branch: "main"
    token: "${GITHUB_TOKEN}"    # fine-grained PAT：仅该仓库 + Contents: RW
  imgbb: { api_key: <原样保留>, expiration: 0 }
```

### 4.3 末帧 JPEG 策略（routers/shots.py `_extract_video_end_frame`——业务层，非 Host 层）

提取 PNG 后、上传前：`PIL` 转 **JPEG q88**（实测 168KB；接力语义只钉位置状态，轻压缩无碍）。
文件名/扩展名交给 Host 按 MIME 处理。注释同步更新 imgbb→Pages。
**首帧两条路径与 Resources rehost 一行不改**——它们传原格式字节，Host 原样托管。

### 4.4 工厂接线（deps.py）

`get_rehost_host()` 改调 `build_image_host()`（image_host.py 已有 kind 分派）并在其中补
`"github_pages"` 分支；ImgbbHost 分支保留（回退开关）。**单例语义保持**（四个调用点拿到
同一个实例——`asyncio.Lock` 才有效）。

## §7 风险与回退

- **Pages 构建 soft limit = 10 builds/hour**（deploy from branch：1 PUT=1 commit=1 build）
  ——**真实吞吐瓶颈是 10 个新文件/小时**，不是 REST 5000 req/h。测试阶段（<30 帧/天，且
  从不集中小时级爆发）可接受；若未来需要密集上传：改「暂存多文件→单 commit→单 build」
  的 git push 支路，或切 custom Actions deployment，或上 R2/GCS——**不拆多仓库绕限**。
- **github.com API 路由抖动**：重试×3 + 轮询闸门兜底；极端情况 config 切回 imgbb（1 行）。
- **容量（精确表述）**：源仓库 recommended 1 GB（GitHub 仓库建议值）；**published Pages site
  上限 1 GB（硬性）**；带宽 100 GB/月 soft。⚠️ git 历史特性：删除旧图**不会**立即使仓库瘦身
  （对象仍在历史包内；GC/历史重写才真正释放）。测试阶段不做 GC；容量真到顶时换新仓库
  （URL 前缀随之切换，canonical 引用由 store 管理，成本一次手术脚本）。
- **token 泄露面**：fine-grained 单仓库 + Contents:RW → 最坏影响=该图床仓库内容可写。
  上传内容仅参考帧（无提示词/日志/密钥——用户已裁定可公开）。
- **回退**：imgbb 线路恢复后 `kind: "imgbb"` 一行即回退；两类并存不互删。
