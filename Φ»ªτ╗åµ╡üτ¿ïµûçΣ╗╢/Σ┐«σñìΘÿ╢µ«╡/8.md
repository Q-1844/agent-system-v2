# 1. 本轮唯一核心目标

S3B.2 只回答一个问题：

> 当前这个 ShotProductionBinding，现在是否仍然可信，并且是否已经具备进入后续生成阶段的条件？

当前：

```text
Shot
  ↓
ShotProductionBinding
  ↓
dependency_fingerprints snapshot
```

S3B.2 要增加：

```text
Shot
  +
ShotProductionBinding
  +
Current Project Canonical
        ↓
Dependency Resolution
        ↓
Current Dependency Fingerprints
        ↓
Compare with Binding Snapshot
        ↓
ShotBindingValidity
        ↓
READY / NOT_READY / UNBOUND
```

以及唯一允许改变 fingerprint snapshot 的操作：

```text
Explicit Refresh
```

本阶段完成以后，系统应该能够可靠回答：

```text
这个 Shot 有没有 binding？

binding 引用的对象现在还存在吗？

仍然 approved / usable 吗？

它们从绑定以后有没有变化？

SceneInstanceView 当前应该解析到哪一个？

ProjectVisualProfile 是否已经设置？

是否有 stale / missing / revoked / invalid dependency？

这个 Shot 现在到底 READY 还是 NOT_READY？

如果用户明确接受当前依赖状态，
怎样显式 refresh snapshot？
```

# 2. 最重要的架构原则

## Principle A — Binding 是 Intent，Validity 是 Projection

`shot_production_bindings.json` 保存的是用户/生产系统明确确认的生产意图。

例如：

```text
Shot s09_c04

Alice
→ look_017

Sword
→ right_hand

Scene
→ scene_instance_004
→ location_view_002
```

它不是 validity cache。

绝对不要新增类似：

```text
binding.status = READY
binding.is_stale = false
binding.valid = true
```

作为持久 Canonical Truth。

正确关系：

```text
ShotProductionBinding
        +
Current Resources
        +
Current Scene System
        +
Current ProjectVisualProfile
        +
Current Shot
        ↓
Derived ShotBindingValidity
```

Validity 必须实时派生。

---

# 3. Read 必须继续零副作用

这是硬规则。

任何：

```text
read binding
read validity
resolve dependencies
check freshness
list validity
```

都不得：

* 创建 `shot_production_bindings.json`
* 修改 binding
* 更新 fingerprint snapshot
* 自动 refresh
* 自动 rebind
* 自动 cleanup orphan
* 自动创建 SceneInstanceView
* 自动 approve dependency
* 自动 regenerate dependency
* 修改任何 Resources canonical
* 修改任何 Scene canonical
* 修改 ProjectVisualProfile

纯读必须是：

```text
read → derive → return
```

不是：

```text
read → fix → return
```

特别防止这种错误：

```text
发现 fingerprint stale
→ Runtime 自动更新 snapshot
→ 返回 READY
```

这是禁止的。

---

# 4. ShotBindingValidity 是 Derived Read Model

请根据当前真实代码设计一个小而明确的 read model。

名称可以根据项目已有命名风格调整，但语义必须明确。

至少应该能够表达：

```text
shot_id
binding_state
readiness
binding_revision

resolved_dependencies
dependency_checks
issues/reasons
```

readiness 至少能够稳定表达：

```text
READY
NOT_READY
UNBOUND
```

关于历史 Shot 是否额外需要：

```text
LEGACY
```

不要仅为了“状态更丰富”自行增加第四种 readiness。

先依据 S3A 最终报告和当前 legacy 行为决定。

核心要求是：

### 无 binding

```text
UNBOUND
```

不报错。

不创建文件。

不自动猜 binding。

### 有 binding 且全部 required dependency 合法并 fresh

```text
READY
```

### 有 binding，但任意 required condition 不成立

```text
NOT_READY
```

# 5. Reason 必须结构化，不只返回一句字符串

后续 S3B.3、UI、Agent 都会消费这个结果，所以不要只返回：

```text
"Shot is not ready."
```

至少要有机器可读 issue。

概念上例如：

```json
{
  "dependency_type": "character_look",
  "dependency_id": "look_017",
  "reason": "fingerprint_mismatch",
  "expected_fingerprint": "...",
  "current_fingerprint": "..."
}
```

但不要机械照抄这个 schema。

请先检查项目现有 error / status / result 风格。

Reason vocabulary 应该小、稳定、确定性。

至少需要覆盖这些语义：

```text
orphan_binding
missing_dependency
unapproved_dependency
revoked_dependency
stale_dependency
fingerprint_mismatch
project_visual_profile_unspecified
cast_mismatch
scene_mismatch
scene_instance_inactive
scene_instance_view_missing
scene_instance_view_ambiguous
binding_conflict
```

如果现有 Resources / Scene System 已经有等价 reason code：

优先复用。

不要无意义创建第二套 vocabulary。

# 6. 必须重新验证 Binding 自身仍与 Shot 一致

S3B.1 在写入时已经做过 validation。

但是 Canonical 后续可以改变。

所以 S3B.2 读取 validity 时不能假设：

> “以前合法，所以现在永远合法。”

必须重新检查当前 Shot。

至少包括：

## Shot 是否仍然存在

如果 binding 存在，但对应 Shot 已被删除：

```text
NOT_READY
reason = orphan_binding
```

Binding 保留。

绝对不要 GC。

绝对不要自动 delete binding。

---

## Shot.scene_id 是否仍匹配

如果 Shot 后续移动/重建导致 scene 关系变化：

重新验证：

```text
binding.scene_id
Shot.scene_id
SceneInstance.story_scene_id
```

不一致：

```text
NOT_READY
```

不要自动移动 binding。

---

## Cast 是否仍匹配

S3B.1 的硬规则继续有效：

```text
binding character set == Shot.characters
```

如果 Shot.characters 后续变化：

```text
NOT_READY
reason = cast_mismatch
```

不要自动补 CharacterBinding。

不要自动删除 CharacterBinding。

---

# 7. Dependency Resolution 必须是精确依赖，不是 project-wide revision

这是 S3B.2 最重要的实现质量标准之一。

假设 Shot 使用：

```text
Alice
Alice Black Coat Look
Wooden Sword
Composition C
SceneInstance S
SceneInstanceView V
ProjectVisualProfile P
```

那么 freshness 只能依赖这些真实 dependency。

不能因为：

```text
Bob Look changed
```

导致 Alice Shot stale。

不能因为：

```text
另一个 Prop changed
```

导致本 Shot stale。

不能因为：

```text
Location 的另一个未使用 View changed
```

导致本 Shot stale。

禁止偷懒使用：

```text
resources.json whole-document revision
scene_system.json whole-document revision
project global modified_at
```

作为 Shot dependency freshness。

否则会制造大量 false stale。

必须尽量复用现有 per-entity / per-generation / per-view fingerprint 机制。

# 8. Fingerprint Snapshot 与 Current Fingerprint

S3B.1 已经在 Binding 中保存：

```text
dependency_fingerprints
```

本阶段：

## Read

重新从当前 canonical 解析同一批 required dependency。

得到：

```text
current fingerprints
```

然后比较：

```text
snapshot fingerprint
vs
current fingerprint
```

如果不同：

```text
NOT_READY
```

并明确指出哪个 dependency changed。

---

## 非常重要：不要修改 snapshot

普通 validity read：

```text
current != snapshot
```

只能得到：

```text
STALE / NOT_READY
```

不能自动：

```text
snapshot = current
```

---

# 9. Fingerprint 必须复用真实领域语义

不要在 `src/shot_binding/` 中重新发明：

```text
Look fingerprint
Prop fingerprint
Composition fingerprint
Scene fingerprint
VisualProfile fingerprint
```

优先调用各领域当前已有稳定 helper / service / read model。

如果现有模块已经公开：

```text
fingerprint()
revision()
basis fingerprint
approved-state fingerprint
stale read model
```

直接复用。

如果没有公开函数，但实现可以安全抽成纯函数：

只做最小、无语义变化的复用。

不要为了 S3B.2 重构 Resources 或 Scene System。

如果某一个 required dependency 当前真的无法得到稳定 entity-level fingerprint：

不要偷偷退回整个 document revision。

请标记：

```text
BLOCKER
```

或明确 deviation，并解释最小解决方案。

# 11. CharacterLook Validity

对于每一个 CharacterBinding：


1. Character 仍存在

4. 当前存在可用的 approved reference
5. 当前 Resources read model 没有把所需 reference 判为 stale / revoked / invalid

# 12. Composition Validity

如果 CharacterBinding 有：

```text
composition_id
```

重新检查：

* composition exists
* character matches
* look_id matches
* composition 当前仍 approved / usable
* required approved reference 仍有效
* fingerprint fresh

如果失败：

```text
NOT_READY
```

但是：

# 不要在这里发明新的 Composition revoke policy

Resources V1 有一个已知政策边界：

```text
Composition 自己已经 approved，
但它内部依赖的 Look 后来发生 revoke/变化时，
Composition 是否应该自动降级
```

这是 Resources approval policy。

不是 Shot Binding policy。

S3B.2 只能消费 Resources 当前已经公开的 verdict。

不要在 Shot Binding 层自行决定：

```text
Look revoked
→ 强制把 Composition canonical 改成 revoked
```

不要修改 Resources。

如果 Resources 当前把 Composition 仍视为 valid：

Shot Binding 按当前公开事实处理。

把该政策边界记录在报告中，不要越权修复。

# 15. SceneInstanceView Resolution

这是 S3B.2 需要真正补上的能力之一。

S3B.1 有：

```text
scene_instance_id
location_view_id
pinned_scene_instance_view_id optional
```

---

## Case A — pinned SIV

如果：

```text
pinned_scene_instance_view_id != null
```

必须使用这个精确 SIV。

重新验证：

```text
exists
belongs to SceneInstance
matches LocationView
approved
current / usable
fingerprint fresh
```

任何失败：

```text
NOT_READY
```

不能偷偷切换成另一个 SIV。

因为 pinned 就代表明确生产选择。

---

## Case B — unpinned SIV

如果没有 pinned SIV：

需要根据：

```text
scene_instance_id
+
location_view_id
```

解析当前合适的 approved SceneInstanceView。

优先复用 Scene System 当前已有的 deterministic selection / approved-view read semantics。

不要在 Shot Binding 中复制 Scene System 的选择规则。

如果：

```text
0 个合法候选
```

则：

```text
NOT_READY
reason = scene_instance_view_missing
```

如果：

```text
存在多个候选，
但 Scene System 本身没有确定性 canonical selection 规则
```

不要随便：

```text
取最后一个
取 created_at 最大
取数组第一项
```

应 fail closed：

```text
NOT_READY
reason = scene_instance_view_ambiguous
```

除非当前 Scene System 已经定义了明确选择语义。

# 16. Unpinned SIV 不能在 Read 时变成 Pin

即使 validity read 成功解析到了：

```text
sciv_123
```

也不能把：

```text
binding.pinned_scene_instance_view_id = sciv_123
```

写回。

Unpinned 本身就是 Binding Intent。

Resolved SIV 属于 derived dependency resolution。

它可以出现在：

```text
ShotBindingValidity.resolved_dependencies
```

但不是新的 Binding canonical。

# 17. SceneInstanceView Freshness

不要只检查：

```text
SIV exists
```

还要消费 Scene System 当前已有：

```text
approval
stale
basis/fingerprint
current-state validity
```

语义。

如果 SceneInstanceView 因：

* relevant SceneState changed
* LocationView changed
* visible anchor changed
* visible prop state changed
* ProjectVisualProfile changed
* reference revoked
* Scene System 自己已有其它 stale reason

而被 Scene System 判定 stale：

Shot：

```text
NOT_READY
```

不要在 Shot Binding 中重新实现一遍 Scene System 的 visible-state projection 算法。

必须复用 Scene System verdict / fingerprint。

# 18. View-relevant state 不能被 Shot Binding 粗粒度化

Scene System 已经建立了：

```text
SceneState = whole-scene truth

SceneInstanceView
= LocationView
+ view-relevant state projection
```

所以 Shot 如果使用 View A：

不可见于 View A 的 state 改变，不应该因为 Shot Binding 自己绑定整个 SceneState revision 而误判 stale。

如果 S3B.1 当前 snapshot 使用的是过粗粒度 SceneState fingerprint：

先检查 S3A 最终设计和真实实现。

不要直接猜。

目标必须保持：

```text
actual visible / resolved dependency
```

而不是：

```text
any SceneState change
```

如果修正需要改变 S3B.1 snapshot representation：

只能做最小、向后兼容的 S3B.2 migration/normalization，并必须在报告中明确 deviation。

不要静默改 schema。

每一个 Bound Shot 必须检查 ProjectVisualProfile。

```text

```

或当前系统等价的 unspecified 状态：

```text

```

不要：

```text
unspecified → fallback default → READY
```


# 20. Explicit Refresh 是本阶段唯一写行为

除 S3B.1 已经存在的 CRUD 外，本阶段新增的唯一核心 mutation 是：

```text
refresh dependency fingerprints
```

它的含义是：

> 用户/未来上层明确确认：继续保留当前 Binding Intent，并接受当前这些 dependency 作为新的 freshness basis。

它不是：

```text
repair
rebind
regenerate
approve
migrate
```

---

# 21. Refresh 的正确流程

概念流程：

```text
load binding
   ↓
validate Shot still exists
   ↓
validate binding structural invariants
   ↓
resolve current dependencies
   ↓
validate dependencies are currently usable
   ↓
compute current fingerprints
   ↓
OCC check expected_revision
   ↓
write new dependency_fingerprints snapshot
   ↓
update binding updated_at / revision according to existing store semantics
```

Refresh 必须：

* project write lock
* expected_revision
* stale revision rejection
* atomic write
* deterministic fingerprints
* no hidden side effects

继续复用 S3B.1 store/OCC。

不要建立第二套 write path。

---

# 22. Refresh 不能掩盖真正 invalid dependency

这是非常重要的。

假设：

```text
Look missing
Look revoked
Prop missing
Composition not approved
SceneInstance inactive
Pinned SIV missing
Profile unspecified
cast mismatch
binding conflict
```

这种情况：

不能因为用户调用 refresh 就把 snapshot 更新后返回 READY。

Refresh 必须 fail closed。

也就是说：

```text
STALE BUT CURRENTLY VALID
→ refresh 可以接受新的 basis

CURRENTLY INVALID
→ refresh 拒绝
```

例如：

### 合法 refresh

```text
Look 内容发生合法更新
→ 新 approved reference 已存在
→ Look 当前 valid
→ fingerprint changed
→ Shot NOT_READY(stale)
→ explicit refresh
→ snapshot 更新
→ Shot READY
```

### 非法 refresh

```text
Look revoked
→ Shot NOT_READY
→ refresh
→ 拒绝
```

不能：

```text
revoked Look fingerprint snapshot 更新
→ READY
```

---

# 23. Refresh 不得改变 Binding Intent

Refresh 只能更新 freshness basis。

不能修改：

```text
look_id
composition_id
prop_id
relation
anchor
scene_instance_id
location_view_id
pinned_scene_instance_view_id
action
production_notes
character set
```

如果用户需要改变这些：

必须走已有 replace/update binding 语义。

不要把 refresh 变成万能 repair API。

---

# 24. Unpinned SIV + Refresh 的特殊规则

如果 binding 是：

```text
scene_instance_id = X
location_view_id = Y
pinned_scene_instance_view_id = null
```

当前 resolve 得到：

```text
SIV A
```

以后 Scene System 产生新的合法 current SIV B。

Validity 可以检测：

```text
resolved dependency / fingerprint changed
→ NOT_READY
```

Explicit refresh 可以接受当前 resolve 结果并更新 dependency snapshot。

但是：

不得把：

```text
pinned_scene_instance_view_id = B
```

写回。

Binding 继续保持 unpinned。

因为：

```text
unpinned = 使用当前该 SceneInstance + LocationView 的合法 resolved visual state
```

而：

```text
pinned = 强制使用某个精确 SIV
```

两种 intent 不同。

---

# 25. Orphan Binding

如果 binding 对应 Shot 已不存在：

返回：

```text
NOT_READY
reason = orphan_binding
```

或当前架构中等价的 explicit orphan classification。

但是：

* 不 delete
* 不 GC
* 不自动归档
* 不创建 replacement Shot
* 不修改 binding

Refresh orphan binding：

必须拒绝。

---

# 26. Legacy / Unbound Shot

旧 Shot 没有 binding：

继续：

```text
UNBOUND
```

不要自动：

* 根据 Character.views 建 binding
* 根据 Shot.characters 猜 Look
* 根据旧 image path 猜 Resource
* 根据现有图片猜 SceneInstanceView
* 根据 prompt 猜 Prop
* 根据 action text 猜关系
* 创建 binding

如果 S3A 最终设计要求额外显示：

```text
legacy = true
```

可以作为 read-model metadata。

但不能因为 legacy 而制造新的 Canonical。

# 32. Fail Closed

以下任何不确定情况都应该优先：

```text
NOT_READY
```

而不是：

```text
best effort READY
```

包括：

* required dependency missing
* fingerprint unavailable
* ambiguous unpinned SIV
* malformed dependency snapshot
* unknown schema
* inconsistent cross-domain identity
* current approval state cannot be established
* stale/invalid source verdict
* required Profile unspecified

但是：

不要把 programmer error 全吞成 NOT_READY。

例如：

```text
unknown shot_binding schema_version
corrupt JSON
unsupported internal format
```

继续按照现有 store 规则显式异常/fail closed。

不要把真正损坏的 canonical 假装成业务 NOT_READY。

# 33. Determinism

同一：

```text

+
same canonical state
```

重复读取 validity：

必须 byte/structurally deterministic（时间戳等非确定字段除外；最好根本不要在 read model 注入 current time）。

Issue ordering 必须稳定。

Dependency ordering 必须稳定。

不能依赖：

```text

filesystem order
glob order
creation race
```

这对后续 Agent / Pack Compiler 很重要。
