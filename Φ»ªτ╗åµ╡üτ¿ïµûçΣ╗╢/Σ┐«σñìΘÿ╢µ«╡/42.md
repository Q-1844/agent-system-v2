## 一、先列全视频生产工具和方法

沿系统 Agent 实际可调用的入口，盘点分镜图生成、素材与场景绑定、视频请求编译、提交与轮询、候选及正式选片、尾帧提取、接缝检查、trace、恢复和下游失效处理。对每项列出：工具入口、代码位置、Agent 能否调用、输入与前置条件、实际 provider 请求、回执与持久化位置、已有实测、失败处理，以及状态〔已验证／仅接通／仅有规则／不可用〕。

方法盘点至少覆盖：独立起镜与正常切镜、真实尾帧作硬首帧、Look 与尾帧融合后作新首帧、单图及多图 reference、硬首帧中的空间转移、首尾关键帧、合格双端之间的桥接、错误端点的独立重生、镜内锚定重试、尾态偏离后的插曲加镜，以及改动正式选片后的下游级联。若发现更多真实入口，也纳入清单。不要为了让清单全绿而强迫每种方法进入正片；可用有明确问题的针对性探针验证。不能执行的路径应保留为明确限制，不能只凭官方文档或编译测试标为“已验证”。

## 三、先查画风漂移，再改锚定规则

以《雨灯归航》已批准的角色、道具和场景资产为准，对比报告所述的贴定义镜头 `s02_c01` 与偏差镜头 `s02_c02`、`s02_c03`、`s03_c01`、修复版 `s03_c03`：逐一追踪实际参考图、引用顺序、scene binding、描述、上一镜尾帧、生成请求和成片首中尾帧。区分“角色身份错误”“同一角色的画风变化”“兜帽或道具状态变化”“空间参考把镜头拉回旧场景”。不要在查明证据前把原因定为 relay 或场景图。

基于已批准资产，为画风、服装／兜帽、道具样式及镜头所需场景状态建立可追溯的锚定和验收条件；先做小范围对照，确认能改善成片，再决定应修改 Binding、描述模板、Skill 决策，还是批准素材本身。需要新增场景或改变剧情时，走系统正式入口及既有人工审批。用户已反馈 s03_c03 原版不可接受、2.5 整体漂移较少；请保留这两项反馈作为验收依据，并提供修复前后可直接观看的对照。

## 四、验证方法的适用边界，而非预设一种万能路线

对有争议且有实际用途的路径做针对性真机测试，至少包括：

* Look＋尾帧双参考：先接通正式 Binding，验证实际请求、素材指代、跨帧身份、画风与空间；若视觉效果不稳，不能因为接口成功就设为默认。
* 硬首帧跨空间：报告已有一次楼梯间进入灯室的成功探针；再由系统 Agent 在真实镜头任务中选择并验证，记录何时优于正常切镜。
* 首尾关键帧桥接：只在两端都是合格且拟保留的视频、接缝确实影响叙事时测试；不得用桥钉住错误端点。
* 错误空间或内容的镜头：比较强化描述、解除 relay 后独立重生、硬首帧连续转场的适用条件。报告中 reference 锁空间只是具体案例，不写成模型的绝对规律。
* 尾态已经偏离但镜头可保留时：让系统 Agent 提出插曲镜，按需要增加镜头数量，并验证故事状态、资产版本与后续依赖；不得静默改写既定结局。

每项均记录“选择前的理由—真实输入与请求—回执—成片观察—反例与禁用条件”。明确区分：请求合法、生成成功、视觉可接受、适合某类叙事任务。抽查首帧、过程帧和尾帧，重点检查角色、画风、道具、场景、动作、故事状态及相邻镜头的剪辑逻辑；画面相似度不能单独决定是否要桥接。用户负责最终审美、剧情接受与正式选片。

## 封板标准与交付

只有以下条件同时成立，才建议宣称“当前范围内的视频 Skill 底层完成”：

1. 正式工具入口、长任务恢复、trace、候选版本与下游失效处理有可复现证据；中断或上游错误不会使已提交任务无故失踪或被当成新任务重复提交。
2. 清单中每条拟用于正式生产的方法均有合法请求、真实 Agent 选择记录、回执及视觉验收；未通过的路径被正确限制，系统 Agent 不会误用。
3. 画风、角色状态、道具和场景锚定经过跨镜实测；《雨灯归航》的关键偏差有明确归因与可观看的改善，或者被诚实列为未解决的封板阻塞。
4. 冻结版本的全新会话测试证明 Agent 会自行加载 Skill、选择适用方法、处理失败、保留真实项目状态，并产出用户可逐镜观看的候选。用户的看片反馈与正式选片分别记录。
5. 与本范围相关的回归没有未解释的关键失败；任何未完成能力有清楚边界和状态，不以文档齐全代替功能完成。
