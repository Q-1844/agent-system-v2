# Phase AI-1B：AI 续写故事

请继续当前已经完成的 Phase AI-1「AI 整理故事」。

本阶段只增加：

**AI 续写故事**

目标流程：

```text
已有完整故事
↓
AI 续写
↓
用户查看 / 修改续写草稿
↓
AI 只整理“新增内容”
↓
新故事段 + 新人物识别
↓
复用现有角色检查 / 匹配 / 创建草稿
↓
用户确认
↓
一次性追加 story_text + Scene[]
```

本阶段不是开放式 Agent。

不要做聊天窗口，不做 AI 导演，不创建 Shot，不生成图片和视频。

---

# 一、这一阶段解决的真实用户问题

用户可能已经完成：

```text
完整故事
+
6 个故事段
+
部分故事段甚至已经存在 Shot
```

后来发现：

> 我还想继续往后讲。

此时不能要求用户：

```text
手动编辑完整故事
→ 再重新整理整个故事
→ 因为已有 Scene 又不能 Apply
```

所以 AI 续写必须是一条专门的 **append-only workflow**。

它只能：

```text
追加完整故事
+
向 Scene 列表末尾追加新的故事段
```

绝不能：

* 修改已有故事文本
* 重写已有 Scene
* 删除已有 Scene
* 修改已有 scene_id
* 修改已有 Shot
* 影响首帧、尾帧、视频或 continuity

---

# 二、入口位置

剧本页增加两个入口，但调用同一个工作流。

## 入口 A：完整故事卡

放在：

```text
完整故事                         [编辑] [AI 续写]
```

这是主要入口。

## 入口 B：故事段列表底部

在：

```text
＋ 添加故事段
```

附近增加一个较低调的：

```text
✨ AI 继续故事
```

它表达的是：

> 当前故事段已经做到这里，我想让故事继续发展。

两个入口都打开同一个 AI 续写工作区。

不要在分镜页面增加“续写故事”。

剧情内容的唯一上游仍然是剧本页。

---

# 三、AI 续写工作区

继续沿用 Phase AI-1 已经使用的大型工作区视觉语言。

不要做小确认框。

建议约：

```text
80vw × 82vh
```

工作区分成三个步骤：

```text
① 续写
② 新故事段与角色
③ 确认追加
```

如果现有 StoryOrganizer 的步骤组件、header、footer 能自然复用，可以提取轻量公共组件。

不要为了复用而大规模重构现有 StoryOrganizer。

---

# 四、Step 1：续写设置

顶部先显示当前故事的结尾，而不是让用户重新读完整故事。

例如：

```text
当前故事结尾

……
赤焰守卫最终锁定了远方的信号，
独自走向被风沙覆盖的城市。
```

建议只显示最后约 300～600 个中文字符。

下面提供一个非常简单的输入：

```text
接下来希望发生什么？（可选）

[                                                   ]
[                                                   ]

不填写则由 AI 根据现有故事自然续写。
```

不要要求：

* 景别
* 镜头数
* 运镜
* 摄影参数
* 首尾帧

这里还是编剧阶段。

---

# 五、续写规模

增加一个非常轻量的选择：

```text
续写规模

[短篇] [标准] [较长]
```

建议语义：

```text
短篇
约新增 1–2 个故事段

标准
约新增 3–4 个故事段

较长
约新增 5–7 个故事段
```

默认：

```text
标准
```

这不是要求模型必须严格生成 N 段。

它只是告诉 AI：

> 这次故事向后推进多少。

不要暴露 token、字数等模型参数。

---

# 六、生成续写

主按钮：

```text
[生成续写]
```

AI 输入至少包含：

* 当前完整故事
* 当前已有故事段的 summary
* 当前项目角色名称与 description_en
* 用户填写的续写方向
* 续写规模
* 项目风格只作为很弱的世界观背景

AI 当前只负责写：

**新的故事正文。**

不要让这一次请求同时返回 Scene JSON。

原因：

* 续写是创作任务
* Scene 拆分是结构化整理任务
* Agnes 2.5 偶尔可能输出非严格 JSON
* 两个职责拆开更稳定

因此这一请求可以直接：

```python
client.chat(..., json_mode=False)
```

返回普通故事文本。

---

# 七、AI 续写 System Prompt

核心要求大致如下。

你是一名影视故事编剧。

请在用户现有故事的基础上继续创作。

要求：

1. 只写新的续写部分。
2. 不重复输出原故事。
3. 延续现有人物、世界观、事件因果和情绪。
4. 不突然改变已经确定的人物身份和关系。
5. 如果用户提供续写方向，优先遵守。
6. 如果用户没有提供方向，根据当前未解决的冲突和目标自然推进。
7. 根据“短篇 / 标准 / 较长”调整剧情推进幅度。
8. 不写摄影术语。
9. 不写 Shot。
10. 不写首帧、尾帧或视频 prompt。
11. 输出可以直接追加到完整故事末尾的正文。
12. 不要以“续写：”“下面是……”等说明性文字开头。

# 八、续写草稿 UI

生成后显示：

```text
AI 续写草稿

赤焰守卫进入城市外围后，
发现信号来自一座废弃通信塔……
……
```

这是可编辑文本框。

用户可以直接修改 AI 草稿。

底部：

```text
[重新续写]

                         [采用并整理新故事段]
```

可以提供一个次级操作：

```text
[仅追加到完整故事]
```

但主路径必须是：

```text
采用并整理新故事段
```

# 九、“重新续写”

点击重新续写：

* 原故事不变化
* Scene 不变化
* 角色不变化
* 只重新生成 continuation draft

用户已经手动修改草稿后点击“重新续写”，需要简单确认：

```text
重新生成会覆盖你对当前续写草稿的修改。

[取消] [重新生成]
```

---

# 十、只处理新增内容

这是本阶段最重要的技术原则之一。

点击：

```text
采用并整理新故事段
```

以后：

不要调用：

```text
organize_story(project.story_text + continuation)
```

再重新整理整个项目。

而应该调用一个类似：

```python
organize_continuation(
    existing_story=project.story_text,
    existing_scenes=project.scenes,
    continuation_text=draft.continuation_text,
)
```

模型真正需要拆分的正文只有：

```text
continuation_text
```

已有 story 和已有 Scene 只作为边界上下文。

---

# 十一、新增 StoryWorkflow 能力

可以基于现有：

```python
StoryWorkflow.organize_story()
```

增加：

```python
async def continue_story(...)
async def organize_continuation(...)
```

例如：

```python
class StoryWorkflow:

    async def continue_story(
        self,
        project: Project,
        direction: str = "",
        scale: str = "standard",
    ) -> str:
        ...

    async def organize_continuation(
        self,
        project: Project,
        continuation_text: str,
    ) -> StoryBreakdownResult:
        ...
```

`continue_story`：

```text
返回普通故事文本
```

`organize_continuation`：

```text
返回 DraftScene[]
```

继续复用 Phase AI-1 已有的：

* DraftScene
* character_mentions
* normalize_name
* match_characters
* CharacterResolution
* 角色草稿生成
* unresolved / matched / created / ignored

不要复制第二套角色解析系统。

---

# 十二、organize_continuation 的上下文

输入给整理模型：

```text
已有故事最后一部分：
...

已有最后 1～2 个故事段：
- ...
- ...

下面是新的续写正文：
...
```

要求：

> 只把“新的续写正文”拆成新的故事段。

已有内容只用于：

* 保证连续
* 理解故事从哪里开始接
* 避免重复前面的故事段

绝不能把已有 Scene 再输出一遍。

---

# 十三、新故事段整理规则

继续沿用 Phase AI-1 已验证的故事段定义：

故事段是：

```text
叙事阶段
```

不是 Shot。

例如新增正文：

```text
赤焰守卫进入城市。
它发现通信塔。
塔下出现一个受伤少女。
两者发生短暂对峙。
```

可以整理为：

```text
新增故事段 1
赤焰守卫进入废弃城市，并找到持续发送信号的通信塔。

新增故事段 2
它在通信塔附近发现一名受伤少女，
双方因为彼此戒备而发生第一次接触。
```

不要拆成：

```text
走路
转头
看塔
抬手
```

# 十四、Step 2：新故事段 + 角色检查

这里尽量直接复用现有 StoryOrganizer 的：

```text
故事段预览
+
角色检查
```

例如：

```text
本次续写将新增 3 个故事段

⑦
赤焰守卫进入废弃城市……
人物：赤焰守卫

⑧
通信塔附近出现一名受伤少女……
人物：赤焰守卫、林夏

⑨
两人决定暂时合作……
人物：赤焰守卫、林夏
```

角色检查：

```text
✓ 赤焰守卫
  已匹配项目角色

⚠ 林夏
  当前项目不存在

[匹配已有角色]
[创建角色草稿]
[忽略角色资产]
```

如果同时新增 5 个角色：

仍然使用统一角色检查列表。

绝不能连续弹 5 个角色窗口。

# 十五、新角色处理

完全复用 Phase AI-1：

```text
matched
created
ignored
unresolved
```

以及：

```text
AI 补全所有缺失角色设定
创建全部角色草稿
```

不自动生成三视图。

如果用户创建角色草稿：

```text
Character(
    name=...,
    description_en=...,
    views={}

```

角色页之后自然显示“尚未生成”。

# 十六、Step 3：最终确认

显示：

```text
本次将：

追加完整故事：
+ XXX 字

新增故事段：
+ 3

新增项目角色：
+ 1
林夏 · 形象待生成

不会修改：
✓ 已有 6 个故事段
✓ 已有 Shot
✓ 已生成图片
✓ 已生成视频
```

这是用户信心非常重要的一步。

主按钮：

```text
[确认追加]
```

次要：

```text
[返回修改]
[取消]
```

# 十七、最终 Apply 必须是 append-only

不要复用当前：

```text
PUT /scenes
```

的“完整对账”语义来做最终续写 Apply。

因为它有：

```text
请求缺失 Scene
→ 删除 Scene
```

这对续写非常危险。

本阶段应该新增一个专门的：

```text
apply continuation
```

后端操作。

概念上：

```python
project = store.load()

validate_draft(project, draft)

project.story_text = append_story(
    project.story_text,
    continuation_text,
)

for draft_scene in new_scenes:
    scene_id = allocate_next_scene_id(project)
    project.scenes.append(
        Scene(
            scene_id=scene_id,
            summary=draft_scene.summary,
            characters=resolved_characters,
        )
    )

store.save(project)
```

必须：

```text
一次 load
→ 一次修改
→ 一次 save
```

不要：

```text
先保存 story_text
→ 再请求 scenes
```

避免：

```text
story 已追加
但 Scene 创建失败
```

这种半完成状态。

新故事段继续使用当前：

```text
next_scene_seq
```

分配。

例如已有：

```text
s01
...
s06
```

新增：

```text
s07
s08
s09
```

* 重新编号旧 Scene
* 重排旧 scene_id

# 十九、现有内容保护

AI 续写成功 Apply 后：

以下数据必须逐对象保持不变：

```text
现有 Scene
现有 Scene.characters
现有 Scene.shots

Shot.description
三个 prompt
批次
首帧
尾帧
视频
continuity
实际视频末帧
```

只允许：

```text
Project.story_text 末尾增加
Project.scenes 末尾增加
Project.characters 增加用户明确创建的新角色草稿
```

# 二十、角色名称匹配在 Apply 时重新确认

AI 续写工作区可能打开几分钟。

期间用户可能在别处创建了新角色。

所以最终 Apply 前：

重新读取：

```text
Project.characters
```

并重新执行一次确定性名称匹配。

例如 draft 中：

```text
林夏 = unresolved
```

但用户期间已经创建：

```text
Project.characters["林夏"]
```

最终应自动变成：

```text
matched
```

不要重复创建。

---

# 二十一、stale 保护

AI 续写 Draft 至少保存：

```text
base_story_text
base_scene_signature
created_at
```

`base_scene_signature` 不需要记录生成资产。

只记录与本阶段相关的结构，例如：

```python
[
    {
        "scene_id": sc.scene_id,
        "summary": sc.summary,
        "characters": sc.characters,
    }
    for sc in project.scenes
]
```

最终确认时：

如果：

```text
story_text 已变化
```

或：

```text
Scene 结构 / 文本已经变化
```

则拒绝 Apply：

```text
故事在 AI 续写期间已经发生变化。

请根据最新故事重新生成续写。
```

不要覆盖。

---

# 二十二、不要因为这些变化判 stale

例如：

```text
角色重新生成三视图
视频任务完成
首帧生成
队列状态变化
角色 views 更新
video_end_frame 更新
```

这些与故事续写没有直接关系。

不要单纯比较：

```text
Project.updated_at
```

否则会产生大量假 stale。

本阶段 stale 应围绕：

```text
story_text
+
Scene narrative structure
```

判断。

建议单独保存：

```text
projects/{p}/output/ai/story_continuation_draft.json
```

至少包含：

```text

base_story_text
base_scene_signature

scale

new_scene_drafts
character_resolution

stage
created_at
```

页面刷新后：

重新打开 AI 续写工作区可以恢复。

不要使用 localStorage 存创作草稿。

# 二十四、草稿状态

建议：

```text
writing
continuation_ready
scenes_ready
ready_to_apply
applied
stale
```

不需要做复杂状态机框架。

只是让刷新恢复时知道应该打开哪一步。

# 二十五、“仅追加到完整故事”

如果实现很简单，可以保留一个次级按钮：

```text
仅追加到完整故事
```

含义：

```text
story_text += continuation_text
```

不创建 Scene。

应用前仍检查：

```text
base_story_text
```

成功后关闭续写工作区。

之后用户可以自行：

```text
编辑完整故事
```

或者以后再处理故事段。

如果这一功能会明显增加实现复杂度，可以本批暂不做。

优先完成：

```text
采用并整理新增故事段
```

# 二十六、用户取消

任何确认前取消：

不得改变：

```text
story_text
```

已经由用户主动点击：

```text
创建角色草稿
```

产生的 Project Character 可以继续保留。

因为“创建到项目”本身就是一个明确的用户操作。

# 二十七、应用完成后的页面

成功以后关闭工作区。

剧本页面：

* 完整故事摘要更新
* 新故事段立即追加到底部
* 已有故事段不闪动、不重新创建
* 新角色 chip 自动显示

可以自动滚动到：

```text
第一个新故事段
```

并短暂显示：

```text
AI 新增
```

用于帮助用户找到新内容。

这个标记只需要是临时 UI，不需要写入数据模型。

# 二十八、AI 续写结果不要自动创造过多新人物

System prompt 增加一条：

> 优先继续使用已有主要人物。只有剧情确实需要时才引入新角色，不要为了增加变化频繁创造新人物。

因为每新增一个长期角色，未来都意味着：

```text
角色设定
→ 三视图
→ 一致性维护
```

这对视频生产成本虽然不是金钱问题，但会增加用户整理成本。

# 二十九、Agnes 2.5 使用

本阶段统一通过当前：

```text
AgnesClient.chat()
```

所以自然使用：

```text
agnes-2.5-flash
```

不要在 StoryWorkflow 中硬编码模型。

续写正文：

```text
json_mode=False
```

续写整理：

继续使用现有 Story Organizer 的结构化 JSON 路径。

如果 organizer 偶发返回不可解析 JSON：

当前可以继续沿用已有错误处理和“重新整理”。

如果实现一个非常小的自动重试很简单，可以在：

```text
JSON parse failure
```

时自动重新请求 **一次**：

```text
Return valid JSON only.
```

最多一次。

不要在本阶段扩展成复杂 JSON repair framework。

# 三十、本阶段不要做

不要实现：

* AI 聊天面板

* AI 修改已有故事中间内容

这仍然是：

```text
AI 编剧 Workflow
```

而不是总控 Agent。

# 三十一、最重要的实际体验

最终用户应该可以这样操作：

```text
我已经做到故事段 6
        ↓
点击「AI 继续故事」
        ↓
输入：
“接下来让赤焰守卫进入城市，
但暂时不要揭示信号来源。”
        ↓
AI 给出续写草稿
        ↓
我稍微修改
        ↓
点击「采用并整理新故事段」
        ↓
AI 整理出故事段 7、8、9
        ↓
发现新人物“林夏”
        ↓
统一角色检查
        ↓
创建林夏角色草稿
        ↓
确认追加
        ↓
故事段 1–6 完全不动
故事段 7–9 出现在后面
```

如果这个体验成立，Phase AI-1B 就成功。
