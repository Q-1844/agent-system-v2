# Claude Code 执行提示词

## Video-First Phase V1 — 视频生成能力测试与自适应生成策略研究

### 一、任务背景与总体目标

你现在接手的是一个已经具备完整故事、资源、场景、分镜、视频生成及部分合成能力的 AI 动画生产系统。

前期已经完成：

* Producer / Script Writer / Resource Agent / Scene Agent / Director 等 Agent 建设。
* Production Resources、Scene System、ProjectVisualProfile。
* ShotProductionBinding、Validity、ShotReferencePack。
* 图片与视频生成链路的多阶段接入和优化。
* 一个可持续复用的 Golden Project。

此前系统主要围绕图片和分镜首帧开展测试。

现在经过真实视频实验，我们观察到：

**A：固定首帧 I2V**

人物与场景相对容易固定，但部分视频开头僵硬，运动自由度受限。

**B：直接 T2V**

动作和运镜表现较好，但人物身份、一致性可能不足。

**C：多参考直接生成视频**

在此前代表性测试中，人物与场景基本能够保持，动作和运镜也有较好表现。

这些是已有实验观察，不是对所有镜头、所有模型都成立的最终结论。

本阶段需要扩大测试范围，通过足够多的真实视频，寻找不同生成模式的能力边界。

核心目标：

> 找到一种兼顾人物、动作、运镜、视觉质量和生成稳定性的生产方式，并逐渐发现不同生成方法的适用条件，最终形成灵活的 Agent 协作模式。

这里的协作模式包括：

* 什么时候直接生成视频。
* 什么时候提供人物或场景参考。
* 什么时候需要预制分镜图片。
* 什么时候需要固定首帧或首尾帧。
* 什么时候应该把复杂动作拆成多个镜头。
* 什么时候使用上一镜尾帧接力。
* 什么时候应允许模型拥有更多运动和构图自由度。

但是，不要预先把上述任何一种方式设定为最终标准。

**先实验，再总结，再固化。**

# 二、本阶段范围和执行边界

本阶段正式名称：

Video-First Phase V1 — Single-Shot Capability & Conditioning Experiment

当前主要完成：

1. 审计现有真实视频生成能力。
2. 复现实验基线。
3. 扩大单镜头视频生成测试。
4. 系统评估人物、动作、运镜等表现。
5. 进行有证据的单变量优化。
6. 总结不同生成方式的适用边界。
7. 提出下一阶段跨视频连续性实验方案。

暂时不要实施：

* 新的 Agent 架构。
* 大型 Generation Policy Engine。
* 全片自动生成策略重构。
* 完整的跨镜头连续性系统。
* 新的 Scene System 或 Resources ontology。
* 新的 Skill。
* 大规模图片生成优化。
* Assembly / Compositor Agent 重构。

如果发现直接影响视频生成的确定性系统 BUG，可以在明确证据后做最小范围修复。

本阶段应以真实视频产出为主要工作，而不是代码开发数量。

# 三、首先审计当前真实状态

在进行任何测试之前，先阅读项目的 CLAUDE.md 和相关仓库说明。

检查：

* git status、branch、HEAD。
* 主仓与子模块当前版本。
* 最近相关 commits。
* 上一阶段视频生成报告及实际产物。
* 当前生产项目、Shot、Binding、ReferencePack 的状态。

不要根据历史报告直接认定代码已经完成某项功能。

重点追踪实际路径：

Shot → Binding → Validity → ReferencePack → Generation Adapter → Video Provider → Video Artifact。

确认：

1. 当前视频能否不依赖首帧直接生成。
2. 是否真正支持多张参考图直接生成视频。
3. 首帧、尾帧以及首尾帧模式如何工作。
4. 视频生成是否仍然强制要求 first frame。
5. T2V、multi-reference、I2V 之间是否存在隐藏 fallback。
6. 当前使用什么模型版本、视频长度、分辨率、比例和参数。
7. Provider 真正收到的参考图顺序及数量。
8. 视频生成后如何记录 candidate、provenance、receipt。
9. 是否能够从真实视频提取末帧。
10. Director、Producer、用户直接调用是否共用生成路径。

特别注意：

如果某种生成模式只是代码里存在名称，却没有真正传递到 Provider，不能记录为已支持。

如果存在可执行接口但没有实际生成成功，也只能记录为尚未完成验证。

完成审计后，形成一份简短的 Capability Inventory。

优先继续使用现有 Golden Project：

`Golden_Full_Production_V1`

先确认它实际存在，并检查当前项目中的故事、场景、人物与视频资产。

不要重新制作一套简单故事替代 Golden Project。

尽量复用现有：

* approved CharacterLook。

* READY Binding。

不得为了测试覆盖已有 approved 资产，也不得随意修改原 Golden Project 的正式镜头选择。

本阶段优先使用现有图片参考。

图片生成限制解除后，可以另外研究高质量风景图、环境图与场景分镜的效果，但不要为了本轮视频测试重新启动大规模生图。

环境镜头可以直接采用 T2V 测试，不需要先准备环境图片。

# 五、建立真实视频测试矩阵

本次不要只反复测试一个表现不错的镜头。

从 Golden Project 中选择约 10～12 个代表性 Shot。

选择依据是镜头能力的差异，而不是随机选择。

必须覆盖以下类别。

| 类别        | 主要测试目标          |
| --------- | --------------- |
| 单人近景 / 特写 | 人脸、身份、表情、景别     |
| 单人全身运动    | 行走、转身、肢体自然度     |
| 人物跟拍      | 人物运动和摄影机协调      |
| 双人互动      | 人数、身份、空间关系      |
| 简单道具交互    | 手部接触、拿取动作       |
| 复杂连续动作    | 动作顺序、物体空间关系     |
| 强运镜       | 推、拉、摇、移等镜头表现    |
| 静态构图中的表演  | 表情、细微动作、自然感     |
| 环境建立镜     | 环境质量、空间感、运动     |
| 风景 / 空镜   | T2V 能否独立产出高质量视频 |
| 室内场景      | 人物与环境的自然融合      |
| 状态变化镜头    | 动作起点和终点是否合理     |

如果某些类别能够合并，可以用一个 Shot 同时测试，但不能因此遗漏关键能力。

尤其要保留此前暴露问题的类型：

* CU 实际生成成 MS。
* 参考场景被当成完整画面复刻。
* 同一个人物出现两个。
* 道具方向突然反转。
* 固定首帧导致前段视频僵硬。

这些应当成为正式实验项目，而不是在报告中简单提一下。

每个 Shot 在实验开始前要明确：

* 预期出场角色数量。
* 核心动作。
* 关键动作顺序。
* 运镜意图。
* 实际需要的景别。
* 重要道具及初始状态。
* 不允许发生的明显错误。

# 六、生成模式设计

本阶段主要比较四种单镜头模式。

### Mode A — Text-to-Video

直接使用文本生成视频，不提供视觉参考。

用于测量模型自身的：

* 运动自由度。
* 镜头语言。
* 人体运动。
* 场景生成。
* 整体自然度。

它不需要先生成分镜图片。

但如果是 BOUND Shot，仍然必须使用项目的生产事实编译正确的文本输入。

**不提供视觉参考，不等于绕过 Binding、Validity 或 ProjectVisualProfile。**

### Mode B — Multi-Reference Video

提供人物、外观、场景等必要参考，但不把任何参考图强制锁定为视频第一帧。

这是本轮的重要候选模式。

初始优先选择最小充分参考：

普通人物镜：

CharacterLook + 必要的 Scene reference。

人物特写：

优先人物身份与外观。

不要因为存在完整场景参考，就强制把全景图片送进去。

关键道具镜：

按需增加 Prop 或 Composition。

参考数量必须依据 Provider 真实能力决定。

不得假设 Agnes 能同时正确理解任意数量的参考。

### Mode C — First-Frame I2V

使用现有可用首帧生成视频。

主要作为受控对照，观察：

* 第一秒是否僵硬。
* 运动能否自然开始。
* 摄影机是否受固定构图限制。
* 身份和场景保持是否更好。

本阶段不把它设定为默认生产方式。

也不要为了运行每个 Case，强制重新生成首帧图片。

### Mode D — First + Last Frame

仅用于确实需要明确动作起点和终点、且现有图片条件合适的镜头。

测试前检查：

* 首尾人物是否一致。
* 物体方向是否合理。
* 动作是否物理连续。
* 中间状态是否能够在视频时长内完成。

如果首尾状态本身矛盾，应记录测试条件存在问题。

不要把不合理的首尾帧强行输入模型，再把失败直接归因于模型能力。

如果当前 Provider 不支持某种模式，明确记录 UNSUPPORTED，不得伪装执行。

**上一镜尾帧接力属于后续跨视频连续性阶段，本轮先不要大规模展开。**

# 七、实验规模与控制变量

本次要求真正扩大样本，而不是只生成几个展示 Demo。

采用分批实验，避免无意义的全组合消耗。

## 第一批：基线复现

优先找到此前 A/B/C 的原始测试 Shot。

如果原始镜头已经不存在，选择相近镜头，但必须说明替代原因。

重新验证：

* T2V。
* Multi-reference。
* First-frame I2V。

保存新生成的视频，与既有结果进行对照。

确认之前发现的差异能否重复出现。

## 第二批：大规模代表镜测试

使用前面选择的 10～12 个 Shot。

每个 Shot 至少选择两种真正适用的生成模式。

每个关键组合尽量进行 2～3 次独立生成。

预计形成约 40～60 条真实视频样本。

注意：不要对所有 Shot 机械执行所有模式。

例如：

纯风景视频不需要强行加入 CharacterLook。

没有合理首尾帧的镜头不需要强行测试 keyframe 模式。

## 第三批：针对性优化与复测

根据前两批结果，选择失败集中或表现有潜力的案例。

追加约 10～20 条针对性视频。

本轮可以把约 50～80 条真实视频作为规划量级，但不是必须凑满的硬指标。

执行前核实模型的实际额度、调用限制和费用。

在可用预算内优先保证实验质量、样本覆盖和有效对照；资源不足时保留完整证据，明确报告实际完成数量及未完成项目。

严禁为凑样本数量产生大量没有可比性的结果。

# 八、控制变量与生成记录

为了让结果能够真正解释原因，每一组对比都必须尽量保持以下条件一致：

* Provider 和模型版本。
* Shot 创作意图。
* ProjectVisualProfile。
* 视频长度。
* 画幅比例。
* 分辨率。
* 关键模型参数。

支持 seed 时记录 seed，并尽量采用配对 seed。

不支持 seed 时记录独立重复次数，不得虚构 seed 控制。

不同生成模式允许针对接口需要调整提示词，但必须保留相同的核心创作目标。

不能出现：

A 模式提示词只写一句话；

B 模式却加入大量详细导演指令；

然后把效果差异归因于参考图片。

每次真实生成必须保存：

* Experiment ID。
* Shot ID。
* Mode。
* 模型版本。
* 最终实际发送的 Prompt。
* 最终实际发送的参考素材及其语义角色。
* 参考数量、顺序。
* 实际参数。
* 生成时间与运行状态。
* 输出 MP4 路径。
* 错误及 receipt。
* 对应的 Binding / Pack basis。
* 评估结果。

记录内容不得包含 API Key、私密凭据或持久化的大段 base64。

视频产物必须可以通过 Experiment ID 重新定位。

---

# 九、重点：生成提示词采用最小充分约束

本阶段不要继续使用不断追加严格限制的方式优化模型。

采取如下原则：

**先给清晰的创作意图，再给必要的生产事实，然后保留模型合理的运动自由度。**

建议每个视频的 Prompt 主要回答：

1. 画面核心主体是谁？
2. 主体在做什么？
3. 动作如何变化？
4. 镜头如何运动？
5. 需要保持的关键身份或状态是什么？

不要无意义重复图片已经表达的信息。

例如参考图片已经清晰表现人物外观，就不需要在文本中反复堆积几十条服装与面部描述。

不要默认添加大量：

STRICTLY、MUST、NEVER、EXACTLY。

也不要默认加入几十项 negative prompt。

这些并非绝对禁用，但每增加一项都应有明确目的。

本阶段可针对相同视频设计三种 Prompt 进行小规模对比：

P1：简洁创作意图。

P2：简洁意图 + 必要的动作时序。

P3：仅针对已观察到的一个具体错误增加明确约束。

一次只改变一个因素。

如果 P3 没有改善，或者明显破坏运动质量，应保留失败记录并撤回该优化。

不要无限追加限制直到某次随机生成成功。

# 十、视频质量评估机制

这是本阶段最重要的验收部分。

**必须评价真实 MP4，而不是只审查首帧、尾帧或 Provider 的成功响应。**

每个视频都应完整播放检查。

可辅助提取多个时间点的帧，但抽帧评估不能代替运动评估。

重点检查以下维度：

### 1. 人物表现

* 人物身份是否正确。
* 脸是否明显变化。
* 服装是否发生非预期变化。
* 是否出现重复人物。
* 是否出现额外路人。
* 表情是否自然。
* 人体结构是否明显异常。

### 2. 动作表现

* 动作是否连贯。
* 是否存在突然跳变。
* 手脚是否明显错位。
* 是否存在违背动作顺序的情况。
* 是否能够完成预期动作。
* 是否自然开始和结束。

重点观察视频开始约一秒内的运动，而不只看中间表现较好的部分。

### 3. 运镜表现

* 是否符合导演意图。
* 推拉摇移是否自然。
* 是否存在不合理的突然变焦。
* 景别是否正确。
* 特写有没有退化成中景。
* 摄影机运动与人物运动是否协调。

### 4. 场景表现

* 环境是否合理。
* 人物是否自然处于场景中。
* 场景是否出现明显结构变化。
* 是否过度复刻参考图片构图。
* 是否保留项目视觉风格。

本轮只评价单条视频内部的场景稳定性。

跨视频场景一致性留到下一阶段。

### 5. 道具与物理关系

* 道具是否正确。
* 是否凭空出现、消失或变形。
* 人物与道具是否真正发生接触。
* 运动方向是否合理。
* 状态变化是否符合预期。

对于复杂手部和刚性道具问题，必须记录具体失败时刻及可复现条件。

不要仅凭一次失败就认定系统或模型存在普遍缺陷。

# 十一、建立可复核的评分和审查结果

每条视频记录上述关键维度的 1～5 分：

1 = 明显失败。

2 = 存在严重问题。

3 = 基本可理解，但需要修正。

4 = 效果良好，具有生产可用性。

5 = 非常好，满足该维度的高质量要求。

此外必须单独标记严重问题，例如：

* 主要人物身份错误。
* 克隆人物。
* 关键道具状态错误。
* 严重动作跳变。
* 镜头意图完全不符。

严重错误不能仅靠其他维度的高分抵消。

对于运动、运镜、表演等主观指标，应尽可能安排独立复核。

如果能够实施盲评，可以隐藏生成模式，让评价者先评价视频，再揭示输入条件。

自动 Vision 工具可以辅助发现：

人物、道具、服装、场景及部分画面问题。

但不要把单张截图的 Vision PASS 当成整条视频质量 PASS。

如果没有真正的视频运动审查能力，就明确保留人工审查状态，不得伪称自动验收通过。

最终输出不仅要有平均分，还要有：

* 各模式的表现分布。
* 严重失败次数。
* 同条件重复生成的稳定性。
* 典型成功案例。
* 典型失败案例。
* 评价者分歧。

样本不足时，不要做出普遍性结论。

---

# 十二、失败归因与优化顺序

每个重要失败都要追查以下路径：

Creative Intent → Binding → ReferencePack → Actual Provider Payload → Generated Video。

分开判断：

**SYSTEM BUG**

系统选择了错误资源，或生成请求、状态、时序、候选管理出现错误。

**ADAPTER / CONDITIONING ISSUE**

正确的生产事实存在，但参考组合、顺序、模式或编译方式造成问题。

**PROMPT ISSUE**

提示词存在冲突、不明确的动作顺序或过度限制。

**REFERENCE ISSUE**

参考图片构图、外观或状态本身不适合目标视频。

**MODEL / PROVIDER LIMITATION**

系统输入正确，经过可重复的控制实验后，模型仍无法稳定完成指定动作。

**INSUFFICIENT EVIDENCE**

现有实验还无法区分原因。

不要因为输出不好就直接修改系统。

优先选择最小范围的单变量实验。

例如人物运动正常但身份不稳定：

先比较有无人物参考。

如果身份得到改善，再尝试增加场景参考。

如果场景参考让人物重新变小、运镜变差，则记录这种条件冲突。

不要立刻开发一套复杂的场景控制系统。

又例如某个连续动作始终失败：

先检查动作起点、终点和时间顺序。

如果该动作确实超出模型能力，可以在后续导演策略中考虑拆镜。

但不能在测试阶段偷偷修改动作目标，再将结果记作原目标成功。

---

# 十三、允许的系统优化范围

如果发现已经证实的确定性问题，可以执行最小修复。

例如：

* 生成模式映射错误。
* 多参考未真正传递。
* 提示词编译重复。
* 错误地强制加载 first frame。
* 视频候选记录错误。
* Prompt 或参考素材 provenance 缺失。
* Provider 能力检查错误。

修复后必须重新执行原失败案例，并与修复前结果比较。

同时运行相关测试与回归。

不要因为某个视频效果不好就改动：

* Resources ontology。
* Scene System ontology。
* Shot schema。
* Binding canonical。
* ReferencePack 核心语义。
* Producer 协作架构。
* Director 的完整职责。

保持：

BOUND + READY → 正式生成。

BOUND + NOT_READY → fail closed。

UNBOUND → 保持现有兼容行为。

有意不向视频模型传某张视觉参考，不代表可以绕过项目事实的有效性检查。

任何优化不得自动批准新资源、静默替换正式候选或降低 Truth Gate。

实验产物应与正式生产资产明确区分。

---

# 十四、本轮结束条件

不能因为执行完预定调用数量就宣称成功。

必须回答：

1. 哪些镜头类型已经能够稳定生成质量较好的视频？
2. 哪些动作最容易失败？
3. 哪些运镜效果较好？
4. 多参考相对于 T2V 的身份收益是否稳定？
5. 固定首帧是否真的持续损害运动？
6. 场景参考在哪些镜头中带来收益，在哪些镜头中存在副作用？
7. 简洁提示词与复杂提示词的效果差异是什么？
8. 哪些问题属于系统，哪些仍属于模型能力？
9. 不同类型的镜头是否需要不同的生成模式？
10. 当前结果是否足以进入跨视频衔接实验？

这里不要求所有镜头全部完美。

但进入下一阶段之前，应至少有一组具有代表性、经过重复生成和审查、能够保留为生产候选的视频。

人物、动作、运镜三个核心维度不能存在尚未解释的普遍性失败。

**如果质量仍未达到要求，继续针对性优化单镜头，而不是提前开始构建跨镜头系统。**

最终是否达到主观成片质量要求，由用户结合真实视频作出验收决定。

---

# 十五、下一阶段研究：跨视频衔接与场景一致性

本轮只制定下一阶段的实验计划，不提前大规模实施。

待单镜头阶段通过后，下一阶段重点研究：

1. 同一人物的连续两个镜头。
2. 同一场景内不同机位。
3. 人物动作跨镜头接续。
4. 服装、道具状态继承。
5. 上一镜真实尾帧接力。
6. 直接生成下一镜并通过参考保持一致。
7. 需要连续运动时使用接力，以及需要真正切镜时避免错误继承。

未来必须专门比较：

普通直接生成下一镜

VS

上一镜尾帧接力生成。

研究内容不仅是画面是否相似，还包括：

* 连续性是否改善。
* 运动是否重新僵硬。
* 运镜是否受到上一镜尾帧限制。
* 切镜节奏是否合理。
* 人物与道具状态是否一致。
* 场景空间关系是否连续。

**连续性不等于让两条视频使用完全相同的构图。**

如果应该从全景切到面部特写，就不能为了连续性强行保留上一镜的完整环境构图。

这类问题属于下一阶段的导演与生成协作研究。

---

# 十六、未来生成协作策略

完成单镜头与跨镜头实验后，再研究真正的 Generation Policy。

未来需要区分两个概念：

**文本分镜 / Shot 创作规划**

负责故事拆分、镜头语言、叙事与动作设计。

**视觉分镜 / 预生成图片**

负责提供具体构图、首帧或关键帧条件。

二者不应混为一谈。

“直接生成视频”不一定意味着不需要导演规划，也不一定需要事先生成分镜图片。

未来应从证据中回答：

* 简单独立镜头能否直接生成？
* 环境镜头是否完全不需要预制图片？
* 人物镜头是否只需 CharacterLook？
* 高精度构图何时需要视觉分镜？
* 明确状态转换何时需要首尾帧？
* 复杂动作何时应该拆镜？
* 连续运动何时需要视频尾帧接力？

不要提前把任何模式设定为唯一答案。

最终策略需要依据：

镜头类型 + 生产事实 + Provider 能力 + 实验结果。

---

# 十七、Skill 的处理

本阶段不要立即添加新的 Skill。

先记录反复出现、能够稳定提升质量的操作模式。

只有当某种方法：

1. 在多个不同镜头中重复有效；
2. 操作步骤已经清楚；
3. 需要 Agent 反复执行；
4. 不能简单通过现有 Prompt 或 Adapter 解决；

才考虑将其整理成 Skill。

未来可能出现的候选包括：

* Video Conditioning Selection。
* Action Decomposition。
* Cross-Shot Continuity。
* Video Quality Review。

这些只是候选方向，并非本轮实施任务。

不要把一次成功生成所采用的提示词直接包装成 Skill。

Skill 必须源于经过重复验证的工作方法。

# 十九、最终执行纪律

整个阶段牢记：

**视频质量优先，但必须具备可解释性和可复现性。**

不要为了测试通过，把复杂动作全部替换成简单站立镜头。

不要为了追求一致性，把所有镜头都重新变成固定首帧 I2V。

不要因为多参考在一条视频中表现良好，就把它设为所有镜头的默认方式。

不要将 Agnes 当前的局限硬编码进整个系统。

不要新增大模块解决尚未验证的问题。

不要用 Mock 视频代替真机。

不要只检查静态截图。

不要让 Agent 自述代替真实结果。

不要隐瞒失败或丢弃不理想的样本。

不要擅自开始全片重生成或正式资源替换。

先确认当前真实代码和额度，再按基线复现、代表镜测试、针对性复测的顺序执行。

最后给出有证据支持的单镜头阶段结论，并明确：

* 哪些模式已经值得继续使用；
* 哪些模式还需要实验；
* 哪些系统问题已经修复；
* 哪些属于暂时无法解决的模型限制；
* 是否满足进入跨视频连续性阶段的条件。

完成本阶段后停止，不要自行开发 Generation Policy Engine、跨视频连续性系统或新 Skill。

本轮最重要的成果不是一套新架构，而是：

**一批真实、高质量、可复核的视频，以及一份能够指导后续生产策略的实验结论。**
